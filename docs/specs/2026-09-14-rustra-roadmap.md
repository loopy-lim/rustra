- 범위: 제품 방향, 요구사항, 단계별 성과, 완료 기준, 1.0 조건

## 1. 방향과 성공의 정의

Rustra의 다음 목표는 **개발자가 Rust 계약 하나를 기존 앱에 연결하고, 그 앱을 계속 변경·배포해도 신뢰할 수 있는 상태**다.

첫 도입에서는 설정과 네이티브 빌드의 막힘을 줄이고, 실사용에서는 계약 불일치와 자원 수명 문제를 예측 가능하게 처리하며, 성능은 실제 앱에서 비용이 큰 경계를 측정해 개선한다. 이 순서를 다음 1.0의 기준으로 삼는다.

제품 설명의 중심은 다음 문장으로 고정한다.

> Rust에서 정의한 명령·타입·이벤트 계약을 여러 호스트에서 재사용하고, 생성물과 실행 중인 네이티브 코드의 불일치를 검출한다.

‘가장 빠른 브릿지’, ‘모든 플랫폼에서 같은 동작’, ‘완전한 zero-copy’는 목표나 기본 홍보 문구로 사용하지 않는다. 호스트별 취소·스레드·채널 차이는 지원 계약의 일부다.

### 선택한 접근

| 접근                                        | 기대 효과                                            | 비용과 한계                                                | 결정                         |
| ------------------------------------------- | ---------------------------------------------------- | ---------------------------------------------------------- | ---------------------------- |
| 도입 흐름을 먼저 완성하고 실제 앱에서 검증  | 외부 개발자의 첫 성공과 유지 사용을 같은 경로로 연결 | 사용자 관찰·소비자 프로젝트 검증이 필요                    | **채택**                     |
| 내부 안정화 전체를 끝낸 뒤 공개 사용성 개선 | 내부 결함을 집중적으로 줄임                          | 실제 도입 병목 발견이 늦고 검증 범위가 계속 늘 수 있음     | 중대한 결함에 한해 우선 적용 |
| 미세 벤치마크 최적화를 먼저 진행            | 특정 호출 성능을 빠르게 개선 가능                    | 설치·업그레이드 실패를 해결하지 못하며 복잡도가 늘 수 있음 | 실측 병목에 한해 후순위 적용 |

사용자 우선순위는 자원 배분 순서다. 데이터 손상·메모리 안전성·계약 우회 문제가 확인되면 안정화가 즉시 선행한다.

## 2. 현재 기준선: 이미 있는 것과 남은 것

2026-09-14에 저장소, 원격 main, GitHub Actions, npm과 crates.io를 읽기 전용으로 확인했다. 아래 ‘구현 존재’는 소스·생성물·워크플로 정의의 확인이다. 최초 SPEC 작성에서 앱이나 전체 테스트를 다시 실행했다는 의미는 아니다. 후속 구현과 로컬 재검증 결과는 10절 및 연결된 실행 기록을 따른다.

npm 9개 패키지의 `gitHead`는 모두 `30c73bd66159f4c777054527236573559c106c98`이다. 현재 main에는 그 이후 watch 변경 유실 수정, UniFFI 렌더러 식별자 검증, 문서 및 예제 산출물 정리가 추가돼 있다. 따라서 **현재 main의 수정이 npm 최신 패키지에 모두 포함됐다고 말할 수 없다.** Rust 0.10.0은 레지스트리 존재를 확인했으며, 이 조회만으로 crate와 현재 main의 소스 일치를 인증하지 않는다.

### 2.3 남은 핵심 간극

1. **저장소 내부 성공과 배포물 소비의 간극.** 기존 온보딩 게이트는 소스가 있는 환경에서 Cargo patch와 JS symlink를 주입한다. 발행 전 검증으로는 유효하지만 레지스트리만 사용하는 신규 사용자와 조건이 다르다.
2. **첫 호출과 실제 앱 유지의 간극.** calculator와 smoke가 앱의 백그라운드 전환, 창 종료, 장시간 부하, 업그레이드·롤백 전체를 대신하지 않는다.
3. **호스트별 증거의 간극.** 현재 매트릭스의 실제 실행 주장은 특정 macOS·RN 시뮬레이터·Android 기기 조합에 한정된다. iOS 실기기와 실제 WebView 수명주기의 증거는 별도로 확보해야 한다.
4. **기본 CI와 주기적 안전성 검사의 간극.** 기본 CI가 성공해도 후속 Miri·Sanitizer 실패를 놓치면 안정성 판단이 잘못된다.
5. **코어 벤치와 체감 성능의 간극.** 직렬화·FFI 미세 벤치 외에 앱 작업의 p95, 네이티브 빌드 대기, CPU·메모리 비용이 필요하다.

## 3. 사용자와 제품 경계

### 우선 사용자

- **1순위:** Rust 코어를 Tauri 또는 React Native 앱에 도입하려는 외부 개발자. 첫 경로는 자신이 쓰는 호스트 하나로 시작하며, 처음부터 멀티호스트 구성을 요구하지 않는다.
- **2순위:** 실제 프로젝트에서 같은 코어를 둘 이상의 기존 호스트에서 사용하거나 네이티브·JS를 함께 업그레이드하는 개발자.
- **3순위:** 기존 Rustra 앱에서 호출량, 큰 payload, 이벤트 처리 또는 개발 반복 시간 때문에 병목을 겪는 개발자.

### 포함 범위

현재 제공하는 Rust/TypeScript 계약, Node/Bun/Tauri/RN 경로, 배포 패키지, 생성 코드, 진단, 호환성, 취소·오류·수명주기, 성능 측정과 개선을 포함한다. 기존 UniFFI 표면은 현재 약속한 범위의 생성·빌드·실행·업그레이드 회귀를 관리한다.

### 이번 로드맵의 비목표

- Electron·Deno·브라우저 WASM·Lynx·RN Windows/macOS 등 신규 호스트의 제품화
- UniFFI Phase 2 이벤트·채널, 신규 언어, 객체 모델 등의 기능 확대
- 범용 UI·렌더러·OS 권한 프레임워크, 새 상태관리·쿼리 프레임워크
- hot-core의 모든 기기 지원 또는 실험 표면 전체의 강제 안정화
- 성능 근거 없는 코덱 교체, 경쟁 도구의 모든 기능 따라잡기
- 다운로드 수·GitHub star 수만으로 1.0을 판단하는 방식

기존 지원 OS에서 실제 실행 증거를 보강하는 일은 신규 호스트 추가와 구별한다. Linux는 현재 **Alpha**로 두고 제품 근거는 빌드·smoke까지 공개한다. 로컬 Linux ARM64 안전성 통과와 릴리스에 요구하는 Actions Linux x86_64 안전성 게이트는 제품 지원 증거와 분리한다. 실제 Tauri WebView의 실행·수명주기와 패키지 설치 영수증을 확보하기 전에는 운영 지원으로 승격하지 않는다. 이 승격은 G1~G4의 필수 조합에 자동 편입하지 않으며, Windows/Linux GUI 등 추가 인증 범위를 1.0의 필수 조건으로 자동 확대하지 않는다.

| A6  | 외부 개발자가 유지보수자의 개별 개입 없이 시작한다                              | 신규 평가자 5명 중 4명 이상이 첫 호출을 완료하고, 도움을 요청한 단계·해결 방법·소요 시간을 기록한다                                                  |

A6의 평가자는 Rust와 해당 JS 호스트를 사용할 수 있으나 Rustra 개발에 참여하지 않은 사람으로 정의한다. 최소 한 명은 Tauri, 한 명은 RN Android, 한 명은 RN iOS를 평가한다. 모집·연락은 후속 실행에서 사용자의 별도 권한과 채널을 따른다.

첫 성공 시간의 제안 목표는 **준비된 Node/Bun 환경 15분, 준비된 Tauri/RN 환경 30분 이내**다. SDK 설치·다운로드 대기는 별도로 기록하고 전체 경과 시간도 함께 남긴다. 초기 다섯 명 표본은 개선 판단용이며 전체 시장의 성공률 추정치가 아니다. 해당 목표는 아직 측정된 실적이 아니다.

| S1  | 초기화·재초기화·종료 순서가 명확하다          | 동시 초기화, 초기화 중 종료, reload 중 호출, 종료 후 호출이 문서화한 결과 하나로 끝난다. 이전 엔진의 늦은 결과가 새 엔진 상태를 변경하지 않는다                 |
| S2  | 자원을 사용한 주체가 정리 책임을 가진다       | 이벤트 구독, 콜백, 채널, pending 호출, 캐시를 종료 후 추적할 수 있다. 닫힌 WebView·언마운트된 컴포넌트로 늦은 전달이 발생하지 않는다                            |
| S3  | 취소·시간 초과·오류 차이를 숨기지 않는다      | 호스트 capability를 기준으로 얕은 취소와 Rust 체크포인트 취소를 구분한다. 타임아웃 이후 실제 작업 지속 여부와 재시도 시 중복 실행 위험을 테스트·문서에 반영한다 |
| S4  | 타입·권한·계약 검증이 같은 호출 경계를 지킨다 | 범위 밖 정수, 잘못된 payload, 구 계약, 권한 없는 명령을 거부한다. generated/native/JS 혼합 버전이 조용히 성공하지 않는다                                        |
| S5  | 실제 앱과 장시간 사용으로 검증한다            | calculator가 아닌 소비자 프로젝트 2개가 대표 업무 흐름을 수행한다. 둘 중 하나는 동일 Rust 계약을 기존 호스트 2개에서 사용한다                                   |
| S6  | 안전성 실패를 추적하고 재현할 수 있다         | Miri·Sanitizer·fuzz의 대상·제외·도구 버전·결과·로그를 보존한다. 알려진 실패가 설명 없이 다음 릴리스로 넘어가지 않는다                                           |

실사용 프로젝트의 앱 전용 도메인 로직은 소비자 저장소에 남긴다. 소비자에서 발견한 공통 브릿지 결함과 최소 재현만 Rustra의 개선 대상으로 가져온다. 이 SPEC은 특정 외부 저장소를 수정하도록 승인하지 않는다.

### 4.3 성능

성능 목표는 사용자의 **작업 완료 지연, CPU·메모리 비용, 개발 반복 대기**다. 작은 함수의 ops/s는 원인 분석 지표로 사용한다.

| ID  | 요구사항                                            | 수용 기준                                                                                                                                          |
| --- | --------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| P1  | 비교 가능한 기준선을 갖춘다                         | 동일 기기·OS·빌드 모드·입력·호출 경로에서 기준판과 후보판을 비교한다. Rust 처리, codec, transport, JS 결과 처리 시간을 가능한 경계에서 분리한다    |
| P2  | 대표 부하를 빠짐없이 본다                           | 작은 scalar, 중첩 데이터, 64 KiB/1 MiB bytes, 연속 이벤트, 동시 호출·취소의 비용을 측정한다. cold/warm 결과를 분리한다                             |
| P3  | 앱에서 큰 비용을 차지하는 병목부터 개선한다         | 실제 소비자 작업 하나 이상에서 p95 지연 또는 작업당 브릿지 CPU 비용 20% 이상 개선을 제안 목표로 삼는다. 기준선에서 비용이 작으면 최적화를 보류한다 |
| P4  | 한 경로의 개선이 다른 경로를 크게 악화시키지 않는다 | 기존 Criterion 10% 회귀 예산을 유지한다. 대표 호스트 흐름에서도 반복 확인된 10% 초과 회귀를 그대로 수용하지 않는다                                 |
| P5  | 빌드·개발 루프도 분리해 측정한다                    | Rust 로직 수정 → 앱 결과 관측, 계약 변경 → 재생성·재빌드 → 결과 관측을 나눠 기록한다. 개선을 선택한 루프는 중앙값 30% 단축을 제안 목표로 한다      |
| P6  | 최적화로 호출 계약을 약화시키지 않는다              | 계약 확인·권한·정수 정확성·취소·자원 정리를 유지하며 테스트를 통과한다. 개선이 없거나 노이즈 범위이면 기존 경로를 유지한다                         |

P3와 P5는 모두 달성해야 1.0이 되는 조건이 아니다. 앱의 병목에 따라 가치 있는 최적화를 선택한다. **1.0의 성능 필수 조건은 비교 가능한 기준선과 설명되지 않은 유의한 회귀가 없는 것**이다.

측정 규칙:

- 각 빌드·기기 조합은 독립 프로세스 또는 앱 재시작으로 최소 5회 측정한다. 같은 실행의 파일 복사본은 반복 횟수에 포함하지 않는다.
- 호출 지연의 p95를 쓰는 측정은 워밍업 뒤 실행당 최소 1,000개 관측을 기본으로 하고, 장시간 작업은 표본 수와 다른 집계 방식을 명시한다.
- SHA, 패키지 버전, artifact hash, 기기, OS, 도구 버전, payload, 동시성, 반복 수, 측정 시각, 분포, 제외 조건을 함께 보관한다.
- CPU·RSS·에너지 측정은 실제 프로세스·기기 측정값을 사용한다. 파일 크기 합을 RSS로 표현하지 않는다.
- 호스팅 CI의 환경 변경이나 thermal throttling은 개선·회귀와 분리한다. baseline 재설정은 ‘성능 통과’와 다른 상태로 남긴다.
- 경쟁 비교는 같은 의미·입력·기기·빌드 조건에서만 부록으로 제공한다. 사용자 가치의 수용 기준을 특정 경쟁 도구 승리로 대체하지 않는다.

### M0 — 현재 상태를 신뢰할 수 있게 만들기

기능 개발보다 먼저 배포 기준과 실패 상태를 정리한다. 핵심 산출물은 정확한 배포 조합표, 알려진 결함 분류, 재현 가능한 안전성 검사 결과다.

**G0 수용 기준**

- npm·crate·생성물·native artifact가 어느 소스를 포함하는지 연결된다. 미발행 수정과 발행 완료를 구분한다.
- 현재 Miri 종료 실패와 Sanitizer exit 1을 각각 재현·분류하고, 필요한 검사가 끝까지 실행되며 진단 로그가 보존된다.
- 재현한 코드 결함은 수정돼야 한다. 도구 제약이면 대상과 제외 이유를 좁혀 기록하고 대체 검증을 둔다. 검사를 통째로 끄거나 설명 없이 실패를 무시하는 것으로 종료하지 않는다.
- 릴리스 후보를 판단할 때 기본 CI 외의 안전성 검사 결과를 함께 확인하는 규칙이 있다. 최신 후보에 필요한 결과가 없으면 미검증으로 남긴다.
- 온보딩·대표 앱·성능의 현재 측정값이 시작점으로 남는다. 실제 사용자 지표가 아직 없으면 ‘미측정’으로 표시한다.

G0는 안전하다는 포괄 인증이 아니다. 이후 단계를 판단할 수 있는 근거를 갖췄다는 뜻이다.

#### M0 실행 계약 — 2026-09-14 보완

| ID   | 공백                                                            | 구현 및 수용 기준                                                                                                                                                                                                                                                                                                 |
| ---- | --------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| M0-1 | lib 테스트가 전역 FFI 풀을 시작해 남은 워커 없이 종료할 수 없음 | 실제 워커·큐 구현을 소유 가능한 풀로 분리한다. 테스트는 소유한 풀을 drop해 sender 해제 → 대기 작업 배출 → 모든 worker join을 검증한다. 전역 운영 풀은 프로세스 수명을 유지하며 새 공개 shutdown ABI를 추가하지 않는다. Miri의 thread/leak 검사를 끄지 않는다.                                                     |
| M0-2 | Sanitizer exit 1의 원인과 로그가 불명                           | 원본 stdout/stderr, 종료 코드, 도구 버전, 실행 SHA, 절대 경로 ASan 보고서를 성공·실패 모두 보존한다. Miri와 같은 원인이라는 가설은 재현으로 판별하며, 다른 원인이면 별도 기록한다.                                                                                                                                |

구현 중 ASan/LSan 재현으로 **재귀 IR의 강한 Arc 순환**을 별도 결함으로 확인했다. 풀 종료를 수정한 뒤 Miri도 동일한 54개 누수를 보고했다. 재귀 역참조는 Weak로 바꾸고 재귀 스키마는 기존 Value 경로를 사용한다. 비재귀 direct 경로와 공개 wire/ABI는 유지하며, 이 결정의 성능 비용은 후속 비교 측정 대상으로 남긴다.

운영 풀을 테스트 때만 우회하거나 `-Zmiri-ignore-leaks`로 숨기는 접근은 채택하지 않는다. 같은 소유 가능한 풀을 운영과 테스트에서 사용하되 소유자의 수명을 다르게 둔다. 자동 idle 종료나 공개 shutdown 추가는 callback 재진입·동시 submit·host unload 계약 변경을 필요로 하므로 이번 수정에 포함하지 않는다. G0의 온보딩·성능·외부 사용자 기준선은 별도 미측정 상태로 남는다.

### M1 — 배포물로 도입하고 변경하기

문서·CLI·패키지·생성물의 성공 경로를 하나의 사용자 여정으로 묶는다. 기존 온보딩·packed consumer 검사는 유지하고, 배포 후 레지스트리 소비와 기존 앱 연결의 증거를 보완한다.

첫 사용 경로는 지원 환경 확인 → 설치 → Rust 명령 정의 → 생성 클라이언트 호출 → 필드 변경 → 도메인 에러 처리 → 이벤트 정리다. 고급 transport·코덱·hot-core 선택은 첫 성공의 필수 지식으로 만들지 않는다.

**G1 수용 기준**

- A1~A6 충족. 최소 인증 조합은 Node/macOS, Bun/macOS, Tauri/macOS 실제 WebView, RN/Android, RN/iOS다. RN은 이 단계에서 emulator/simulator도 허용하되 증거 수준을 표시한다.
- 기존 앱 연결은 Tauri 1건, React Native 1건 이상에서 검증한다. 새 템플릿 성공만으로 대체하지 않는다.
- 발행된 정확한 버전의 설치·생성·호출 영수증이 있으며, 저장소 내부 patch/symlink가 없는지 확인한다.
- 발견된 도입 실패 중 영향이 큰 최대 3개를 해결하고 새 평가로 결과를 확인한다. 실패가 없으면 관측 결과를 그대로 남긴다. 평가자 미확보 상태는 외부 도입 완료로 표시하지 않는다.
- 업그레이드 및 한 단계 롤백을 배포물로 수행한다. 기존 패키지 버전 숫자의 강제 통일은 요구하지 않는다.

### M2 — 실제 앱에서 안정성 증명하기

대표 소비자 2개에서 설치 이후의 사용을 검증한다. 두 프로젝트는 앱 목적과 사용 흐름이 달라야 하며 같은 calculator를 이름만 바꾼 사례로 채우지 않는다. 최소 한 흐름은 명령·이벤트·실패·취소·종료를 함께 사용한다.

**G2 수용 기준**

- S1~S7 충족. 두 소비자가 각각 최소 4주 동안 사용 기록을 남기고, 연속 두 번의 배포 버전 업그레이드를 완료한다. 달력 경과만으로 채우지 않고 실행 빈도·주요 작업·문제 기록을 남긴다.
- Tauri/macOS 실제 창 생성·탐색·종료, RN/Android 실기기와 RN/iOS 실기기의 전경·배경 전환·reload·종료를 검증한다.
- 대표 수명주기 100회 반복에서 중복 전달, 종료 후 호출 반영, unhandled 오류가 없다. 예상된 취소·타임아웃은 별도 집계한다.
- 대표 부하를 조합별로 최소 2시간 지속한다. 채널·구독·pending 호출이 정리 후 기준값으로 돌아오고, warm-up 뒤 RSS 증가 추세가 설명되지 않은 채 남지 않는다. 2시간 실행과 4주 사용 기록은 서로 대체하지 않는다.
- 오버로드·잘못된 입력·계약 불일치에서 데이터 손상이나 조용한 성공이 없다. 복구·재시도 여부가 오류 계약과 일치한다.
- 기본 CI·안전성 검사·호스트 검증의 실패가 원인과 상태 없이 남아 있지 않다. 단위 테스트 성공을 물리 기기 검증으로 승격하지 않는다.

iOS 실기기 접근이 없으면 Android·desktop 증거는 계속 확보할 수 있다. 다만 RN/iOS의 G2와 그 범위를 포함한 1.0 인증은 미완료로 유지한다.

### M3 — 실제 비용이 큰 병목 개선하기

P1~P6을 적용한다. 도메인 계산 비용이 대부분이면 브릿지 최적화로 사용자 체감이 개선되지 않을 수 있으므로, 먼저 비용 비중을 확인한다.

후보의 우선순위는 **영향받는 실제 작업 수 × 그 작업에서 브릿지가 차지하는 비용 × 개선 확신도 ÷ 변경·검증 비용**으로 판단한다. 측정치가 없는 후보에 임의 점수를 부여하지 않는다.

**G3 수용 기준**

- 대표 호스트·부하의 비교 가능한 기준선과 원본 결과가 있다.
- 선택한 병목은 P3 또는 P5의 목표에 대한 달성·미달·보류 사유를 남긴다. 이득이 노이즈 수준이면 변경을 채택하지 않는 것도 유효한 결론이다.
- 개선 전후에 같은 안정성·정확성 검증을 통과하고, 다른 대표 경로의 유의한 10% 초과 회귀가 남지 않는다.
- 최소 한 개 실제 소비자 시나리오에서 성능 결과를 확인한다. 코어 미세 벤치만 개선된 경우 결과 범위를 그렇게 제한한다.
- hot-core를 평가한다면 메모리 누적·재시작 필요·지원 기기 한계까지 포함한다. 개발 편의를 이유로 실험 표면을 자동으로 기본 경로에 넣지 않는다.

### M4 — 1.0은 증명된 범위에 대해 선언하기

**G4 수용 기준**

1. G0~G3를 충족한다. 요구사항별 근거가 문서·소스 존재, 자동 검사, 배포물 소비, 실제 호스트, 실기기, 장시간 사용 중 어느 수준인지 명시돼 있다.
2. 데이터 손상, 메모리 안전성 위반, 권한·계약 검사 우회, 기본 설치·호출 불능을 일으키는 알려진 릴리스 차단 결함이 0개다.
3. 1.0 후보의 공개 Rust/TS API·wire·FFI·생성 계약을 동결하고, 최소 4주와 연속 두 번의 후보 배포 동안 소비자 검증을 수행한다. 공개 계약을 다시 깨면 영향을 받은 후보 관찰을 다시 시작한다.
4. 1.0 기본 사용 경로가 hot-core·inspector 등 실험 표면에 의존하지 않는다. 나머지 공개 표면에는 기존 버전·폐기 정책을 적용한다.
5. Node/Bun/Tauri/RN의 인증 조합과 미인증 조합을 함께 공개한다. M1의 최소 조합에 M2의 모바일 실기기 검증이 더해져야 한다. 기존 지원 OS 표기는 근거에 따라 유지하며 새 플랫폼 인증을 묵시적으로 약속하지 않는다.
6. 기존 UniFFI Phase 1은 생성·모바일 smoke·업그레이드 회귀를 통과한다. 이벤트·채널·취소의 TS 동등성이나 Phase 2 완성은 1.0 조건이 아니다.
7. 외부 개발자가 따라갈 설치·오류 해결·업그레이드·롤백 문서가 최신 배포물과 일치하고, 주요 경로는 EN/KO 모두 제공한다.
8. 발행 후보와 검증 artifact가 연결되고, 발행 후 실제 레지스트리 소비 결과가 남는다. 발행·배포·연락 권한은 이 SPEC이 부여하지 않는다.

1.0의 대상은 핵심 Rustra 계약과 이를 제공하는 패키지의 안정성 약속이다. 보조 패키지까지 모두 같은 숫자로 발행할 필요는 없다. 구체적인 패키지별 버전은 기존 독립 릴리스 정책과 changeset으로 결정한다.

## 6. 지표와 증거 운영

| 지표         | 측정 단위                                 | 초기 목표                                 | 해석 주의                          |
| ------------ | ----------------------------------------- | ----------------------------------------- | ---------------------------------- |
| 첫 호출 성공 | 신규 평가자별 호스트·단계·개입 여부       | 5명 중 4명 이상                           | 소표본 탐색 지표                   |
| 첫 성공 시간 | 준비된 환경 시간 + 전체 경과 시간         | Node/Bun 15분, Tauri/RN 30분              | SDK 대기를 숨기지 않음             |
| 지속 사용    | 비계산기 소비자·실제 사용 기간·업그레이드 | 2개 프로젝트, 각 4주, 연속 2회 업그레이드 | 프로젝트 수만으로 안정성 판단 금지 |
| 릴리스 품질  | 차단 결함·호환 조합·소비자 결과           | 차단 결함 0, 모든 필수 조합 통과          | 전체 CI 배지 하나로 합치지 않음    |
| 런타임 성능  | 대표 작업 p50/p95, 처리량, CPU/RSS        | 선택 병목 20% 개선 제안, 10% 회귀 예산    | 같은 조건과 독립 반복 필요         |
| 개발 반복    | 수정부터 결과 관측까지                    | 선택 루프 중앙값 30% 개선 제안            | 로직 변경·계약 변경 구분           |

수용 기준의 수치는 초기 제품 목표다. 현재 달성 수치가 아니며, 첫 기준선에서 비용과 분산을 확인한 뒤 SPEC 개정으로 조정할 수 있다. 목표를 낮추거나 지원 범위를 바꿀 때는 근거·영향·대체 검증을 기록하며 완료 상태를 소급해서 만들지 않는다.

각 증거에는 요구사항 ID, 후보 SHA/버전, 환경, 실행 시각, 관측 결과, 실패 또는 제외 이유, 원본 로그·artifact 위치가 연결돼야 한다. 같은 SHA의 최신 검사 실패가 나오면 그보다 오래된 성공 기록만으로 현재 통과를 주장하지 않는다.

## 7. 범위·일정이 흔들릴 때의 결정 규칙

| 상황                                   | 결정                                                                        |
| -------------------------------------- | --------------------------------------------------------------------------- |
| 도입 실패와 성능 후보가 동시에 있음    | A2~A5를 막는 문제를 먼저 처리                                               |
| 중대한 안전성·데이터 손상 문제 발견    | 다른 개선을 중단하고 재현·영향 범위·복구·회귀 근거 확보                     |
| 외부 평가자 또는 실기기 미확보         | 독립 검증은 계속 진행하되 해당 수용 기준은 미완료 유지                      |
| 특정 호스트의 낮은 수요·높은 검증 비용 | 기존 지원 약속은 유지하고 추가 인증 확대를 보류. 지원 축소는 별도 정책 결정 |
| 성능 이득이 작고 구현 복잡도·위험이 큼 | 최적화 보류, 측정과 결론만 유지                                             |
| 신규 플랫폼·새 기능 요청 발생          | 본 로드맵에 자동 편입하지 않고 별도 SPEC 후보로 분리                        |
| 1.0 조건이 일정 안에 충족되지 않음     | 0.x 개선 릴리스를 이어가고 검증 기준을 낮추지 않음                          |

운영의 기본은 두 주마다 도입 병목, 실사용 결함, 성능 측정 결과를 함께 검토하는 것이다. ‘도입 → 안정성 → 성능’ 우선순위를 유지하며, 완료 항목을 다시 새 기능으로 제안하지 않도록 기준선과 요구사항 상태를 갱신한다.

## 8. 기존 로드맵과의 관계

[2026-09-01 로드맵](../plans/2026-09-01-roadmap-design.md)의 도입·증거 중심 방향은 계승한다. 다음 항목은 현재 소스와 사용자 지시로 재분류한다.

| 과거 항목                                                 | 이번 SPEC의 처리                                                            |
| --------------------------------------------------------- | --------------------------------------------------------------------------- |
| 이벤트 표면, CLI 진단, 타입화 에러, React bigint·Suspense | 구현 존재. M1 사용자 여정과 M2 회귀 검증에 편입                             |
| 문서 영어화·온보딩·코드젠 검사                            | 이미 기반 존재. 배포물 소비와 사용자 관찰로 검증 수준 보강                  |
| 계약 게이트·공개 API 안정화                               | 기존 계약과 검사 유지. 업그레이드와 실패 경로 증거 강화                     |
| 성능 CI 게이트                                            | 이미 존재. 실제 호스트·앱 작업과 개발 반복 측정으로 보완                    |
| Electron·Deno·WASM 등 확대                                | 사용자 지시에 따라 이번 범위 제외                                           |
| 모든 실험 표면·모든 OS 증거를 1.0 전에 완결               | 인증 범위를 명시하는 방식으로 변경. 기본 경로의 실험 의존은 제거            |
| 0.6 → 0.7 → 0.8 → 1.0이라는 버전별 일정                   | 현재 0.10 기준의 M0~M4 성과 단계로 대체. 버전 번호를 일정으로 사용하지 않음 |

과거 설계·감사 기록은 당시 근거로 보존한다. M0 실행 PLAN은 본 SPEC의 요구사항과 현재 소스를 대조해 작성·실행했다. M1~M4는 별도 후속 PLAN으로 작업을 도출한다. 이 문서에는 작업별 파일 수정 목록, 실행 명령 순서, 커밋 분할이나 구현 코드를 두지 않는다.

### 외부 1차 자료의 적용

[UniFFI 공식 가이드](https://mozilla.github.io/uniffi-rs/latest/)는 바인딩 생성과 각 플랫폼으로 라이브러리를 전달하는 일을 구분한다. Rustra 역시 생성 성공과 설치·실행 성공을 분리해 평가한다. [Tauri 공식 Rust 호출 문서](https://v2.tauri.app/develop/calling-rust/)와 [NAPI-RS 시작 가이드](https://napi.rs/docs/introduction/getting-started)는 이미 각 호스트의 연결 경로를 제공한다. 따라서 Rustra의 투자 방향을 계약 재사용·도입·업그레이드 품질에 집중하는 것은 이 자료와 현재 구현을 바탕으로 한 제품 판단이다. 경쟁 도구에 특정 기능이 ‘전혀 없다’는 배타적 주장은 이 SPEC의 근거로 삼지 않는다.

### 다음 작업자에게 전달할 내용

- 확정된 사용자 결정: 도입 1순위, 실사용 안정성 2순위, 성능 3순위. 플랫폼 확대 제외.
- 확정된 이번 산출물: 본 SPEC과 M0-1~~M0-5의 PLAN·구현·검증 기록. M1~~M4는 후속 작업이다.
- 실행 전 갱신할 사실: main/배포 SHA, 레지스트리 버전, Miri·Sanitizer를 포함한 최신 검사 상태, 실제 평가자·기기 가용성.
- 보존할 계약: 독립 패키지 버전, 호스트별 capability 차이, UniFFI와 TS의 경계, 실험 표면 구분, 증거 수준 구분.
- M1~M4 후속 PLAN이 정할 것: 실제 작업량·담당·일정·수정 파일·검증 순서. 본 SPEC의 우선순위·비목표·수용 기준 변경은 먼저 이 문서에 반영.

문서 작성 완료는 M0~M4 또는 Rustra 1.0 달성을 뜻하지 않는다. 각 단계의 성과는 해당 수용 기준의 실행 증거가 확보된 뒤에만 완료로 표시한다.

## 10. M0 후속 구현 결과

2026-09-14 요청한 M0-1~M0-5를 [PLAN](../plans/2026-09-14-m0-safety-release.md)에 따라 구현하고 [로컬 실행 검증](../verification/2026-09-14-m0-safety-release.md)을 마쳤다. Miri 213개, ASan/LSan 178개, Fuzz 3개 각각 601초를 Linux ARM64에서 통과했다.

[G0 성능 기준선 PLAN](../plans/2026-09-14-g0-performance-baseline.md)에 따라 재귀 complex route의 release A/B도 기준/후보 각각 5개 독립 프로세스로 측정했다. 비재귀 oneOf/map control은 -0.50%/+1.93%로 10% 예산 안이었고, 재귀 depth 1/8은 안전한 Value fallback 때문에 3.89x/3.13x 느렸다. 호출마다 IR을 다시 검사하던 비재귀 공통 비용은 제거했다. [원본 영수증](../benchmark-receipts/2026-09-14-m0-complex-route-ab.json)은 이 결과를 Rust 코어 경계로 제한한다.

플랫폼 지원 표기도 함께 정리했다. Linux는 Alpha이며 현재 제품 근거는 빌드·smoke까지다. 최신 후보의 Linux ARM64 Miri·ASan/LSan·Fuzz는 로컬 통과했고, Actions Linux x86_64 게이트는 아직 실행하지 않았다. 컨테이너 안전성 통과를 실제 Linux GUI·패키지 설치 증거로 승격하지 않는다.

이는 원격 Actions·발행·host/실기기·실제 소비자 검증 및 G0의 남은 온보딩·사용자 기준선을 대신하지 않는다. 특히 G3의 실제 소비자 p95 또는 CPU 개선을 달성했다는 뜻이 아니다.
