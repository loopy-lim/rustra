# Migrating from 0.5 to 0.6

0.6 is a pre-1.0 minor release on the Rust crate line (`rustra` and
`rustra-macros` 0.5 → 0.6). It carries the stabilization track: new optional
`rustra.json` sections, editor support via a published JSON Schema, a
multi-target `rustra doctor`, and formal compatibility gates. Most changes are
additive — an existing valid `rustra.json` keeps loading unchanged, and no
wire, contract-hash, or FFI surface moves. The one behavioral change to plan
for is doctor's new build checks, which can turn a broken Rust setup from a
pass into exit 1.

## 1. Versions

```toml
[dependencies]
rustra = "0.6"
rustra-macros = "0.6"
```

The npm side no longer has a single shared version. The compatibility anchor is
`@rustra/types`: every adapter depends on `^0.6.0`. The CLI features described
below land with the next `@rustra/cli` minor — until that release, the
published CLI's `init` and `doctor` output does not include them.

## 2. rustra.json: `$schema`, `dev`, and `inspector` sections

All additions are optional; existing configs need no edits.

- `$schema` is now accepted at the config root. Before, it was rejected by the
  fail-closed unknown-key check. `rustra init` emits it pointing at the JSON
  Schema shipped inside the `@rustra/cli` package
  (`./node_modules/@rustra/cli/rustra.schema.json`), so editors get
  autocomplete and validation without any URL fetch. Adding it to an existing
  config is optional.
- `dev` and `inspector` are new optional sections. `dev.target` selects
  `native` (default) or `wasm`; `dev.wasm` carries `engine` (`wasm3` only) and
  `parityGate`; `inspector.onMismatch` selects `diagnose` or `ignore`. The
  loader collects every cross-field violation into one error list — for
  example, `dev.target: "wasm"` without a `reactNative` section names both the
  missing section and any invalid `engine` value instead of failing on the
  first one.
- Unknown keys still fail closed, and the known-key set grew to include the new
  sections. If you assert on loader error messages, the "Known keys" list now
  mentions them.

```json
{
  "$schema": "./node_modules/@rustra/cli/rustra.schema.json",
  "schema": "./generated/schema.json",
  "output": "./src/generated",
  "node": {}
}
```

## 3. `rustra init` output

- The generated config is minimal: `$schema`, `schema`, `output`, and the host
  section(s) only. The previous template pinned
  `codegen.rustBinary`/`node.rustBinary` explicitly; the fallback selection
  picks the same binaries in the scaffold layout (`generate` for codegen, the
  package binary for node), so projects keep working without those keys. Add
  them back only when your layout has multiple candidates.
- Host sections are chosen by detection: a `react-native*` entry in the target
  project's `package.json` adds the `reactNative` section, and the generated
  `Cargo.toml` then declares a `staticlib` `[lib]` section to match.
  `--host node|react-native` overrides detection.
- Scripts that diff or parse `rustra init` output will see the new key order
  and shape.

## 4. `rustra doctor`: multi-target matrix and new build checks

- Configs with two or more host sections get a per-target status matrix
  (`target / build / contract / runtime / notes`). One section failing does not
  stop the others from being checked; the exit code reflects the worst state.
  Host sections pointing at different Rust backends produce a
  `config.rust_consistency` warning ("one project, one contract").
- New `section.<target>.build` checks are collected for `node`, `bun`, and
  `reactNative` sections — even in single-section configs, where no matrix is
  printed. They verify that the Cargo manifest resolves, exactly one package
  matches, and the required binary/cdylib/staticlib target exists. These
  checks are required: a broken Rust setup now makes doctor exit 1 where it
  previously passed. CI jobs that call `rustra doctor` can newly fail — fix
  the underlying build configuration (`crate-type`, `node.rustBinary`,
  `bun.rustLibrary`, …) rather than removing the call.
- Machine-readable consumers (`--format json`): the `checks` array gains the
  `section.*.build` and `config.rust_consistency` ids, and the `matrix` field
  appears only for multi-section configs.

## 5. API, FFI, and wire: no action

- No FFI symbol was added or removed. The public Rust and TypeScript export
  lists are pinned by an API-surface snapshot gate, and internal items are now
  tagged `#[doc(hidden)]` / `@internal` — exports did not move.
- The wire format and the contract-hash algorithm are unchanged. Wire
  back-compatibility is now enforced by golden fixtures
  (`packages/types/src/backcompat.test.ts`) instead of convention.
- `RendererHost` status is unchanged: `#[doc(hidden)]` and deprecated,
  retained for the remainder of the 0.x cycle (see
  [versioning policy](../versioning-policy.md)).
- CI gained a wasm32-unknown-unknown compile check for the core crate. It
  affects contributors only.

## 6. Verification and rollback

```bash
bun install --frozen-lockfile
bun run test:types
bunx --bun @rustra/cli doctor --config rustra.json
bun run test:release-coherence
bun run test:compat
```

Per app, verify a real Node process, real Bun FFI, and the Tauri release
build, as in the [0.3 to 0.4 guide](./0.3-to-0.4.md). Roll back by pinning the
previous versions: `rustra = "0.5"` in Cargo and the previous `@rustra/*`
ranges in package.json — move `@rustra/types` and every adapter to that same
range together, since it is the shared anchor. crates.io versions cannot be
deleted or replaced.
