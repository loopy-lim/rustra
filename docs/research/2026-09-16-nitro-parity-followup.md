# Nitro 잔여 차이 후속 검증

기존 공개 경로에서 남은 성능 차이를 실행 순서, 호출 비용, 실제 DFS, 큰 객체 변환으로 나누어 검증했다. 최종 채택 여부와 공개 경로 재측정은 아래에 구분한다. 이 문서는 [기존 잔여 분석](2026-09-16-nitro-parity-gap-analysis.md) 이후의 실행 기록이다.

## 측정으로 확인한 차이

### Android 버퍼는 실행 순서에 민감하다

기존 측정과 동일한 16개 네이티브 라이브러리를 사용해 별도 `rustra-nitro-diagnostic/v1` 프로토콜로 40개 독립 프로세스를 실행했다. 두 버퍼 크기 × 네 실행 방식 × 다섯 실행이며, 1,860개 샘플의 정확한 체크섬을 재검증했다. 제외한 실행은 없다.

| 크기        | 실행 방식         | Rustra 평균 µs | Nitro 평균 µs |
| ----------- | ----------------- | -------------: | ------------: |
| 64 KiB      | 각자 독립 실행    |         13.758 |        15.124 |
| 64 KiB      | 교대, Rustra 시작 |          5.888 |         8.534 |
| 64 KiB      | 교대, Nitro 시작  |          7.431 |         5.568 |
| 1,048,571 B | 각자 독립 실행    |        259.562 |       139.501 |
| 1,048,571 B | 교대, Rustra 시작 |         30.887 |       211.112 |
| 1,048,571 B | 교대, Nitro 시작  |        259.791 |        40.109 |

교대 시작과 사전 검증 순서를 함께 바꾸자 긴 지연이 발생하는 쪽이 바뀌었다. 단순한 복사 속도나 Rust/C++ 언어 차이만으로 기존 버퍼 평균을 설명할 수 없다. GC를 강제하거나 외부 메모리 보고를 줄이지 않았다. GC 이벤트를 샘플과 연결해 수집하지 않았으므로 GC가 직접 원인이라고 확정하지 않는다. 고정된 실험 순서 때문에 독립 실행 간 열·시간 경과 영향도 분리되지 않았다.

이는 Android 물리 기기의 진단 결과다. iOS에서 같은 순서 실험을 검증한 결과는 아니다. 기존 v2의 합격 기준과 원본을 바꾸거나 이 결과를 공개 성능 판정에 대신 넣지 않는다. [전체 진단 결과와 바이너리 식별 정보](../benchmark-receipts/2026-09-16-nitro-buffer-order-diagnostic.json).

### 작은 호출의 고정 비용

기존 iOS Simulator 공개 동기 경로의 중앙값 차이는 add 약 64 ns, string 112 ns, pair 148 ns, indexed 166–176 ns였다. Android는 string 179 ns, pair 267 ns, indexed 219–237 ns였다. 전체 호출 차이이며 특정 검사 하나의 비용으로 볼 수 없다.

JS 클로저를 합친 후보는 첫 설정에서 함수 호출 하나를 줄였지만 재설정 이후에는 호출 하나가 늘고 이전 네이티브 클로저를 유지했다. 기존 동작 검사와 후보 검사는 통과했으나 이 절충 때문에 성능 채택 전에 폐기했다. 실제 Rust framed 경로는 이미 정적 Package와 Command를 빌리고 있어 반복 Arc/shape 복제가 발견되지 않았다. 소유권·세대·오류 경계를 줄이는 변경은 채택하지 않았다.

### 실제 DFS와 자료 배치

별도 호스트 진단은 실제 Rust 명령과 Nitro C++ 탐색/저장 본문, 생성된 DTO 선언을 사용한다. DFS 대신 인덱스를 쓰거나 fixture 알고리즘을 바꾸지 않는다. JSI/FFI가 없는 macOS arm64 진단이며, 휴대폰이나 iOS 앱의 성능 수치로 승격하지 않는다.

첫 탐색용 다섯 실행에서 Rustra/Nitro 평균 비율은 balanced255 1.034, balanced1023 1.055, balanced8191 1.013, wide1025 0.783이었다. 호스트의 노드 크기는 Rust 128 B, C++ 152 B였지만 외부 문자열·맵·자식 배열 메모리를 포함하지 않는다. 이 수치만으로 캐시나 캐스팅을 원인으로 확정할 수 없다. 검토에서 입력 capacity를 resident capacity처럼 표시한 점과 호스트 loader의 네이티브 생성 과정 차이를 발견했다. 원본 측정은 보존하고, 별도 비계측 실행으로 실제 보관 용량과 스택 확장을 관찰했다. 이 새 관찰의 바이너리는 원래 시간 측정과 다르며 원래 비율을 소급 인증하지 않는다.

균형 트리 뒤에 넓은 트리를 저장하면 Nitro는 노드 용량 8,191과 비어 있는 자식 벡터의 할당 513개를 유지했다. Rust는 새 트리를 이동해 노드 용량 1,025, 비어 있는 자식 벡터의 할당 0개였다. DFS 스택은 큰 균형 트리에서 Rust `1→4→8→16`, C++ `1→2→4→8→16`으로 확장됐다. 넓은 트리는 각각 초기 할당 뒤 9회와 10회 확장됐다. 실제 TypeScript fixture 네 개의 모든 필드는 양쪽 보관 데이터와 일치했다. 이런 차이는 자료 배치·저장 정책 관찰이며 어느 차이가 시간을 지배하는지 확정한 프로파일은 아니다. [원본·비계측 결과 및 재현 절차](../benchmark-receipts/2026-09-16-nitro-core-diagnostic.json).

## 채택하지 않은 직렬화 후보

큰 postcard 응답은 작은 caller buffer 시도가 실패하면 전체 크기 계산과 실제 인코딩을 수행한다. 크기 계산을 제거하는 bounded heap flavor를 만들어 한도, 전체 초과 크기, 늦은 Serialize 오류 우선순위, 핸들러 한 번 실행, 버퍼 소유권을 검사했다. 관련 13개 검증은 통과했다.

그러나 같은 release 바이너리에서 8,191노드 출력의 여섯 AB/BA 쌍을 비교한 결과, 첫 후보는 평균 10.04%, 중복 바이트 계산을 줄인 두 번째 후보는 17.55% 느렸다. 두 후보를 폐기하고 원래 코드를 복원했다. 직렬화 순회 감소가 실제 시간 감소를 보장하지 않는 사례다. 작은 f64 대조군은 최적화로 약 1 ns 수준이 되어 공개 호출의 무회귀 근거로 쓰지 않는다. [두 후보의 원본·코드·측정값](../benchmark-receipts/2026-09-16-nitro-postcard-rejected.json).

## 작은 맵 코덱 후보

생성 C++ 인코더의 primitive map은 이전에 항목 수와 무관하게 임시 vector를 만들었다. 4개 이하의 항목을 각 호출이 소유하는 고정 저장소에 담고, 더 큰 맵은 기존 vector 경로를 사용한다. 기존 최대 용량 검사와 최대 64개 초기 예약, 한 번의 값 읽기, UTF-8 키 정렬을 유지했다. 전체 트리의 알고리즘·표현은 바꾸지 않았다.

실제 Hermes 인코더에서 기존 코드와 후보를 비교했다. 같은 입력에 대한 전체 wire 바이트를 TS 기준과 측정 전후로 대조했다. 각 연산은 새 Writer를 만들고 측정 안에서 출력 소비와 해제를 완료한다. 독립 프로세스 90개, 추가로 짧은 맵의 배치를 늘린 별도 프로토콜 50개를 실행했고 제외한 결과는 없다.

| 입력             | 후보/기존 비율 |      95% 구간 |
| ---------------- | -------------: | ------------: |
| 균형 255         |         0.9828 | 0.9669–0.9989 |
| 균형 1,023       |         0.9833 | 0.9761–0.9907 |
| 균형 8,191       |         0.9915 | 0.9847–0.9983 |
| 넓은 1,025       |         0.9687 | 0.9502–0.9876 |
| 맵 0개, 큰 배치  |         1.0121 | 0.9778–1.0477 |
| 맵 4개, 큰 배치  |         0.9847 | 0.9726–0.9970 |
| 맵 5개, 큰 배치  |         1.0017 | 0.9794–1.0245 |
| 맵 64개, 큰 배치 |         1.0050 | 0.9942–1.0160 |
| 맵 65개, 큰 배치 |         1.0063 | 1.0003–1.0124 |

트리 인코딩은 약 0.9–3.1% 개선됐다. 65개 맵은 약 0.6% 느려졌으며 다른 크기에서도 변동은 남는다. 위 숫자는 인코더 대조군이고 전체 호출 개선율이나 Nitro 상대 성능이 아니다. JSON으로 재구성한 입력의 객체 배치는 앱에서 직접 만든 객체와 다를 수 있다. 여러 탐색적 비교의 명목 95% 구간이며 다중 비교 보정은 하지 않았다. [모든 대조군과 코드·바이너리 근거](../benchmark-receipts/2026-09-16-nitro-small-map-control.json).

실제 Hermes의 1,129개 단언과 관련 생성기 검사 17개가 통과했다. 초기 검사 실패는 이전·후보 코드에서 동일했다. 기본 테스트용 Hermes의 블록 스코프 설정 때문에 반복문 getter가 마지막 변수를 함께 참조한 원인이었고, getter 팩터리로 바꿔 값·순서·횟수 검사 자체는 유지했다. 사용자 요청에 따라 새 무작위 스트레스 검사는 하지 않았다.

bare React Native 예제는 기존에 생성된 계약·코덱이 뒤처져 있었다. 전체 생성물을 현재 CLI로 일관되게 갱신하고 두 RN 예제의 codegen 검사를 통과시켰다. 이 유지보수 변경은 위 작은 맵 성능 개선량으로 계산하지 않는다.

## 최종 공개 경로 결과

작은 맵 코덱 후보를 유지하고, 고정한 새 Release 앱을 iOS Simulator와 물리 Android에서 각각 다섯 번 실행했다. 각 실행의 90개 항목이 정답·소유권·receipt 검증을 통과했다. 소스 fingerprint는 `47653b4b6c2d81f815a0d034bab71fb8f2aebefa934cb1a648ea03296fe67275`이며, 317개 소스 입력과 205개 설치 입력을 고정했다. [전체 원본·식별 정보·180개 판정](../benchmark-receipts/2026-09-16-nitro-parity-followup.json).

| 환경           | 공개 동기: 동급 이상 / 느림 / 미확정 | Promise API: 동급 이상 / 느림 / 미확정 | 내부 진단: 동급 이상 / 느림 / 미확정 |
| -------------- | ------------------------------------ | -------------------------------------- | ------------------------------------ |
| iOS Simulator  | 20 / 9 / 1                           | 19 / 9 / 2                             | 19 / 8 / 3                           |
| Android 실기기 | 20 / 8 / 2                           | 20 / 8 / 2                             | 19 / 8 / 3                           |

**공개 동기는 40/60, Promise API는 39/60이 동급 이상이며 전 항목 목표는 아직 미달이다.** 이전 후보는 각각 37/60, 38/60이었다. 서로 다른 실행 집단이므로 합격 항목 증가를 작은 맵 변경 하나의 인과적 효과로 계산하지 않는다. 독립 인코더 대조군의 개선과 전체 공개 경로 판정을 함께 보아야 한다. 특히 버퍼의 판정은 고정 v2 순서에 한정되며, 위 Android 진단에서 드러난 순서 의존성을 반영해 해석한다.

남은 주요 차이는 작은 문자열·pair·indexed 호출, iOS의 큰 균형 트리 resident DFS, 일부 Android resident·버퍼·큰 데이터 작업이다. 상세 수치가 불확실한 항목도 아래 표에서 유지한다. 클로저 변경·postcard 후보를 폐기한 이유와 맵 65개 대조군의 작은 손해도 위에서 함께 공개했다.

다음 조사 지점은 작은 결과의 문자열 소유권·JS 속성 생성과 framed 경계 비용을 계측으로 나누는 것이다. ABI 교체나 JSI handle 캐시는 근거를 추가로 확보한 뒤 결정해야 한다. 큰 트리의 앱 내 차이를 설명하려면 실제 대상 아키텍처에서 루프·자료 배치·메모리 회수 이벤트를 연결한 프로파일이 필요하다. 현재 호스트 DFS 결과나 전체 sync/Promise 차이를 특정 단계의 순수 비용으로 환산하지 않는다.

## 검증 범위와 실행 결정

- main RN의 iOS/Android Release 빌드 및 각 5회 전체 행렬, 실제 Hermes 1,129개 단언, 생성기 17개 검사와 두 RN의 codegen 검사를 수행했다. 새 무작위 스트레스·fuzz·Linux LSan 또는 새 발행을 수행한 것으로 표시하지 않는다.
- 버퍼 진단은 Android에 한정한다. 현재 Hermes 헤더에는 GC 계측 인터페이스가 있지만 고정한 앱에서 샘플별 GC 기록을 수집하지 않아 직접 원인은 미확정이다. iOS 버퍼 순서 실험을 수행한 것으로 표시하지 않는다.
- 동일 호스트의 일반 최적화 빌드를 사용했으나 Rust LLVM과 Apple clang, 기본 LTO와 최적화 장벽이 동일하다고 주장하지 않는다. DFS 비계측 기록과 원래 시간 측정의 바이너리 차이도 보존했다.
- 클로저 후보는 재설정 후 호출 증가·이전 클로저 보유 때문에 device A/B 전에 기각했다. postcard 후보 두 개는 계약 검증 통과 뒤 실제 시간 악화로 기각했다. 크기나 명령 이름에 따른 결과 생략은 없다.
- bare 예제의 생성물 누락은 동일 CLI로 일관되게 갱신했다. 별도 성능 향상으로 계산하지 않는다. 설치가 없던 개발 의존성은 고정 lockfile로 설치했고, 타입 검사와 iOS/Android 자동 연결 검사가 통과했다. 이는 별도 bare 앱의 네이티브 빌드·실행 검증을 뜻하지 않는다.
- 원본·중간 실패·기각 후보와 판단 근거를 보존한다. 빌드 보조 스크립트의 기기 ID 치환 오류는 앱 실행 전 실패였고, 올바른 기기 ID로 재개한 빌드만 최종 행렬에 사용했다. 새 프로세스의 성능 표본을 임의 제외하지 않았다.
- 이전 커밋 이후 승인된 범위에서 계속 진행했다. 보조 스크립트 실행 권한 문제는 설치된 스킬을 변경하지 않고 로컬 호출 방식으로 해결했다. 진단 자료 보완은 런타임 구현과 별도 파일에서 수행하고, 부모가 모든 빌드·측정 순서를 관리했다.

최종 독립 검토는 명세·품질 모두 통과했고 조치할 발견은 없었다. 원본에서 180개 판정과 고정 입력 686개 해시를 대조했다. 코덱 개선(`7f2f2b2b`), bare 생성물 갱신(`9f90e4e4`), 진단 도구(`e10b00b4`)를 별도 로컬 커밋으로 정리했다. 발행·버전 변경은 포함하지 않는다.

## 전체 행렬
