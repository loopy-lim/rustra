# 리서치: WASM 호스트 — 경쟁 격차 #1 해소를 위한 사실 수집

**날짜**: 2026-09-07
**기준 체크아웃**: `.worktrees/integrate` (feat/integrate-1.0-track, 5472ff60)
**격차 정의**: `docs/research/2026-09-07-competitive-landscape.md:40` — "**웹/WASM 호스트
부재** — 가장 큰 시장 공백(FRB·napi-rs·wasm-bindgen 대비)." 같은 문서 종합부(:67)는
시급 격차 1순위로 WASM을 든다. `docs/plans/2026-09-07-platform-interop-followup.md:24`는
"WASM 호스트(격차 #1, **별도 설계 필요**)"로 명시 — 본 문서와 짝하는 설계 문서가
그 "별도 설계"다.

**방법**: 코드 실측(아래 모든 file:line은 integrate 워크트리 기준) + 로컬 실험 3종
(wasm32 빌드/실행/계측, 2026-09-07 본 머신 macOS arm64). 실험 재현 명령과 결과를
근거 블록에 그대로 싣는다. 외부 지식은 "미확인"으로 분리 표기.

## 요약

코어는 **이미 wasm32-unknown-unknown으로 컴파일된다** (CI 게이트 + 로컬 재현). 런타임
위험은 컴파일이 아니라 세 곳에 국한된다: (1) async 워커 풀의 `std::thread::spawn`은
wasm에서 트랩 — 단, 지연 초기화라 sync 엔트리만 쓰면 도달 불가(스파이크가 기기에서
증명), (2) 실행기 `block_on`의 `thread::park`는 wasm에서 **즉시 반환(no-op) — Pending
future는 무한 busy-spin**(본 리서치 실험으로 신규 확인, 종래 "파크 불가" 인식과 다름),
(3) 32개 `rustra_ffi_*` exports는 전부 wasm exports로 그대로 노출되지만 포인터 인자는
선형 메모리 오프셋 스테이징 ABI를 필요로 한다(스파이크가 spike-local 6함수로 프로토타이핑).
이벤트는 코어에 FFI drain 엔트리가 없어(엔진 바이너리가 자체 구현) 신규 export가
필요하다. 바이너리 크기 실측: 2-커맨드 엔진 raw 882 KiB / gzip 217 KiB / brotli 168 KiB.
순수 JS WebAssembly 호스트에서의 동기 invoke 왕복은 1.56 µs/호 — Node napi
rkyv V2 기준선(2.91 µs, followup 문서 실측)보다 빠르다.

## 1. 기존 wasm32 지원 상태

### 1.1 CI `rust-wasm32` 잡 — 컴파일 check만, 테스트 없음

`.github/workflows/ci.yml:119-129`:

- 툴체인: rust 1.95.0 + `targets: wasm32-unknown-unknown` (:124-126).
- 명령: `cargo check -p rustra --target wasm32-unknown-unknown` (:129).
  **check 레벨**이다 — `--all-targets` 아님(테스트/벤치 미검증), clippy 아님,
  빌드 산출(.wasm)도 없다. 주석(:114-118)은 "컴파일만 단언하고 테스트 실행은
  아키텍처 제약으로 범위 밖"이라고 명시하며 hard gate 유지를 선언한다.
- gate 잡의 필수 집계에 포함 (:540, :562, :577) — wasm32 컴파일 파손은 머지를 막는다.

**로컬 재현(2026-09-07)**: 동일 명령으로 `Finished dev profile in 2.63s` —
의존성(postcard 1.1.3, sha2, serde_json, schemars 등) 전체가 wasm32로 컴파일됨을
확인. `rustra-macros`/`rustra-naming`은 각각 proc-macro/순수 로직 크레이트라
타깃이 아닌 호스트에서만 빌드된다.

### 1.2 코어 크레이트에는 wasm cfg 게이트가 전혀 없다

`grep -rn "cfg(target" crates/rustra/src/` — **0건**. 유일한 target-specific
의존성은 Tauri 기능데이터다: `crates/rustra/Cargo.toml:16,27`의
`tauri = { version = "2", optional = true }` (feature `tauri`). wasm32 check는
feature 기본값(tauri off)으로 통과한다. 즉 현재 상태는 "게이트 없이 우연히
컴파일됨"이 아니라, **스파이크가 검증한 인과관계**(1.3)에 기댄 설계다:
`ffi_pool.rs`의 스레드 스폰은 지연 초기화(`OnceLock`)라 wasm 경로에서 도달하지 않는다.

`platform.rs:47,91`과 `builder_platform.rs:157`의 "wasm" 언급은 `#[command(platform(...))]`
속성의 **미지원 대상 예시**일 뿐(`None`이면 스텁 유지가 정상) — wasm 실행 코드가 아니다.

### 1.3 RN wasm3 스파이크(A0) — 기기 검증 선례

`examples/rn-wasm-spike/` (Task A0, 2026-08-31, VERDICT: PASS). 핵심 사실:

- `docs/compatibility-matrix.md:127-147`: iOS 시뮬레이터 + Android 에뮬레이터에서
  실제 `.wasm`(wasm3 v0.9.1 해석) 실행, postcard 응답이 native staticlib과
  **바이트 동일**(`double(21)` → `01010c7b2276616c7565223a34327d00`), 계약 해시도
  native/wasm 간 동일(`e79b7f01…`). 실행 중 엔진 스왑(OTA drop)도 통과.
- `examples/rn-wasm-spike/NOTES.md` "Core patches required: NONE" —
  **코어 패치 0건**으로 sync FFI 엔트리만으로 왕복이 성립했다. 단 scope caveats:
  "sync commands only (the async worker pool would panic on wasm32 without
  atomics)" (:143-144), 스테이징은 spike-local `spike_alloc`/`spike_unstage`

- 스파이크 백엔드는 standalone workspace(`backend/Cargo.toml`에 `[workspace]` —
  루트 workspace와 격리), crate-type `["rlib","staticlib","cdylib"]`,
  release profile `opt-level = "s"`, `panic = "abort"`.

### 1.4 CLI `dev.target = "wasm"` 오케스트레이션(A3) — 이미 착지

`docs/compatibility-matrix.md:184-213` + `packages/cli/src/dev-config.ts`:

- `rustra dev`가 코드젠 후 `cargo build --manifest-path <..> --target
wasm32-unknown-unknown --release`를 돌리고 산출 경로를 공지
  (`[dev:wasm] engine artifact: <path>`). 아티팩트명은 lib target 이름에서 파생.
- doctor: wasm32 타깃 미설치는 **필수 fail**(`doctor-checks.ts:369-375`),
  "wasm dev는 cooperative-only — 릴리스 전 native 검증" 경고는 warn
  (`doctor-checks.ts:349-360`).
- release guard: 발행 패키지 `files`에 wasm 백엔드(wasm3 소스, `*.wasm`,
  `wasm32*` 산출)가 섞이면 release-coherence 스크립트가 실패 — **dev-only
  격리**가 계약이다(compatibility-matrix.md:209-213).

즉 "WASM 호스트" 트랙의 출발점은 백지가 아니라: 컴파일 게이트(O), 기기 증명(O,
RN/wasm3 경유), 빌드 오케스트레이션(O, dev 타깃), JS 호스트 어댑터·패키지·런타임
증거(X) 상태다.

## 2. 코어의 wasm 비호환 요소 전수 조사

### 2.1 `ffi_pool.rs` — async 워커 풀: spawn은 트랩, 도달 가능성은 지연 초기화가 차단

- `ffi_pool.rs:54-92` `async_pool()`: `std::sync::mpsc::sync_channel` +
  `std::thread::spawn` 2개(ASYNC_POOL_SIZE=2, :13). `OnceLock` 지연 초기화.
- 초기화 트리거는 async FFI 엔트리뿐이다 — `rustra_ffi_invoke_async`/
  `_json_async`/`_rkyv_v2_async*`(`NOTES.md` "Why the async worker pool is not
  a wasm hazard here" 절, ffi_async_entries.rs/ffi_typed_async.rs).
- **실험 1 (2026-09-07, 본 머신)**: wasm32-unknown-unknown release(panic=abort)
  최소 크레이트에서 `std::thread::spawn(|| 1u32).join()` export 호출 →
  Node WebAssembly에서 `RuntimeError: unreachable`(panic이 abort로 컴파일된 트랩).
  같은 실험에서 `std::thread::park()`는 **예외 없이 즉시 반환**했다(2.2 참조).
- mpsc `SyncSender`도 마찬가지로 spawn 없이는 워커가 없어 소비 불가 — 풀 전체가
  wasm에서 무의미하다. 스파이크 NOTES의 production 권고 #1이 정확히 이것:
  "`#[cfg]`-gate `ffi_pool.rs`/`ffi_workers.rs` for `target_family = "wasm"` so
  async entries either return `invoke.unsupported_on_wasm` error frames or run
  inline". 아직 미착지(코어에 cfg 0건, §1.2).

### 2.2 `executor.rs` — `block_on`: park는 no-op로 즉시 반환 → Pending은 무한 busy-spin

- `executor.rs:37-48` `block_on`: `Poll::Pending → thread::park()` 루프.
  `ThreadWaker::wake`는 `unpark` 기반(:9-18).
- **실험 1 결과(위)의 함의**: wasm32-unknown-unknown(원자적 시설 없음)에서
  `thread::park()`는 블록하지 않고 즉시 반환한다. 따라서 Pending future를 넘기면
  `block_on`은 park-폴링이 아닌 **즉시 재폴링 무한 루프**(hot spin, JS 스레드
  영구 점유 + 100% CPU)가 된다. "파크가 불가능해 걸린다"는 통념과 달리
  **조용한 갇힘이 아니라 발열 갇힘**이다 — 본 리서치의 신규 실측 사실.
- 유일한 호출처는 매크로 생성 async 커맨드 래퍼다: `rustra-macros/src/macro_command.rs:255`
  `rustra::__private::block_on(async move {...})` (코어 내부 직접 호출은
  `private.rs:4`의 재수출뿐). 즉 **async fn 커맨드를 sync FFI 엔트리로 호출하면
  wasm에서 block_on에 진입한다**. 첫 poll에 완결하는 future(대기 없는 async fn)면
  정상 동작 — Pending이면 busy-spin. 스파이크는 sync fn 커맨드만 다뤄 이 경로를
  밟지 않았다(NOTES.md "sync commands only").
- wasm 전용 대안(명시적 펌프를 future에 주입하는 등)은 코어에 존재하지 않는다 —
  `grep -rn "block_on"` 결과 `executor.rs`, `private.rs` 2파일뿐.

### 2.3 FFI 표면 — extern "C" 32식은 전부 wasm exports로 노출됨, 단 ABI는 선형 메모리 스테이징 필요

전수 목록(`grep 'pub unsafe extern "C"'` + `pub extern "C"`, 테스트 제외):
dispatch 계열 `rustra_ffi_invoke`/`_json`/`_json_into`/`_postcard`(ffi_sync_entries.rs,
ffi_buffer_entries.rs), rkyv V2 계열 `rustra_ffi_invoke_rkyv_v2`/`_into`/
`_async`/`_async_into`(ffi_typed_entries.rs:14, ffi_typed_buffer.rs:32,
ffi_typed_async.rs:12,95), 버퍼/로우 `rustra_ffi_invoke_buffer`/`_raw`/
`has_buffer`/`has_raw`(ffi_typed_entries.rs:48,103,81; ffi_typed_buffer.rs:5),
async JSON `rustra_ffi_invoke_async`/`_json_async`(ffi_async_entries.rs:25,92),
라이프사이클 `rustra_ffi_free`/`_free_owned_bytes`/`_invoke_cancel`/
`_cancellation_status`/`_set_max_payload`/`_get_max_payload`
(ffi_lifecycle_entries.rs:111,157,44,57,81,92), 스키마 `rustra_ffi_get_schema`/
`_contract_hash`/`_schema_generation`(ffi_schema_entries.rs:38,67,87),
이벤트 `rustra_ffi_event_sink_register`/`_unregister`(ffi_event_entries.rs:38,76),
채널 `rustra_ffi_channel_create`/`_create_bytes`/`_send`/`_send_bytes`/`_drop`
(ffi_channel.rs:208,237,265,285,304), 핫리로드 `rustra_ffi_hot_reload`
(ffi_hot_reload.rs:164), 스냅샷 `rustra_ffi_capture_snapshot`(ffi_snapshot.rs:130).

**실험 2 (2026-09-07)**: 스파이크 백엔드(0.8.0 기준 재빌드)를 Node
`WebAssembly.instantiate`로 적재 — `WebAssembly.Module.exports()`로 확인한
exports는 위 core 32식 전부 + spike 6식 + `memory` = 39개(`rustra_mobile_init`은 코어 export가 아니라 `mobile_entry!` 매크로가 소비자 크레이트에 생성하는 심볼 — entry.rs:6-12). **코어 수정 없이
extern "C" → wasm export 매핑이 1:1로 성립**한다(실험 로그: §6.4 참조).

그러나 ABI 의미는 다르다:

- **raw pointer 인자**(`*const u8`/`*mut u8`/`*mut usize`)는 wasm에서 **선형
  메모리 내 오프셋**으로 재해석된다. JS는 wasm 메모리 밖 버퍼를 포인터로 넘길 수
  없으므로 (a) 요청 바이트를 wasm 메모리에 먼저 기록하고, (b) out_len 같은
  out-파라미터도 wasm 메모리의 슬롯으로 줘야 한다 — 스파이크의 6단계 스테이징
  프로토콜(`NOTES.md` "wasm call protocol", `wasm3-smoke-main.c:60-81`):
  `off = spike_alloc(len)` → host writes at `memory[off..]` →
  `len_off = spike_alloc(4)` zeroed → `resp_off = spike_invoke(off, len, len_off)`
  → **memory grow 가능성 때문에 매 호출 뷰 재동기화** → u32LE 길이 판독/복사 →
  `spike_free(resp_off, resp_len)`/`spike_unstage(off, len)`.
- **함수 포인터 인자**(async 완료 콜백 `on_complete`, 이벤트/채널 싱크 콜백)는
  wasm에서 **호스트 함수 import**(JS 함수를 import로 제공)로만 실현된다.
  `FfiEventCallback`/`FfiChannelCallback`(ffi_event_entries.rs:38,
  ffi_channel.rs:13-25) 타입은 wasm 모듈 입장에서 import 시그니처가 된다.
  본 리서치는 이 경로를 실험하지 않았다 — **미확인**(구현 난이도·성능).
- **해제 경계 대응**: `alloc_response`(ffi_prelude.rs:97-115)는 반환 포인터 앞에
  8바이트 헤더(매직 `0x52555354` "RUST"/메모리상 LE 바이트열 "TSUR" + u32 LE 길이)를
  심고, `rustra_ffi_free`(ffi_lifecycle_entries.rs:111-146)가 그 헤더로
  `Box<[u8]>` 복원 + 매직 무효화 + (debug) free_guard 오용 abort
  (ffi_free_guard.rs). 이 계약은 wasm에서도 그대로 유효하다 — 포인터가
  오프셋일 뿐, 해제 책임(정확한 (ptr,len) 1회)과 헤더 레이아웃은 동일.
  `rustra_ffi_free_owned_bytes`(헤더 없는 짝, :157-173)도 동일.

### 2.4 OS/libc 의존 — 코어에는 사실상 없다

- `grep -rn "libc\|std::process\|std::fs\|std::net\|std::os::"` 결과:
  `std::process::abort`는 debug free_guard 경계뿐(ffi_lifecycle_entries.rs:122,168;
  wasm에서 abort는 트랩으로 컴파일 — panic=abort 프로파일과 동일 계열), 파일/소켓/OS
  프리미티브 사용은 0건. dev-dependencies의 tempfile/criterion은 wasm 타깃
  빌드에 포함되지 않는다(cargo check 통과로 실증).
- `std::time::Instant`는 ffi_pool.rs 테스트(:199)에서만 — 테스트는 wasm에서
  돌리지 않는다(CI check-only).

### 2.5 이벤트/채널 전달 표면의 공백 — 코어에 drain FFI가 없다

- 이벤트 버스 `EventBus::take_pending_events`(events_bus.rs:51)는 **Rust API일
  뿐, FFI export가 아니다.** `__drainEvents` 폴링 커맨드는 엔진 바이너리 쪽에서
  자체 구현한다 — `examples/calculator/src/loop_stdio.rs:18,245,281`
  (예약 cmd id drain, NDJSON `__drainEvents`와 동일 페이로드). wasm 호스트는
  "엔진 바이너리의 loop main"에 해당하는 층이 없으므로, 폴링 drain을 쓰려면
  **코어에 이벤트 drain export 신설**이 필요하다.
- 푸시 경로(`rustra_ffi_event_sink_register`, emit → C 콜백 즉시 호출,
  events_state.rs의 `deliver_via_sink`)은 함수 포인터 인자라 §2.3의 import
  이슈가 그대로 적용된다.
- 채널(`ChannelHost`, channels_handles.rs:24-49 핸들 u32 + `rustra_ffi_channel_send`
  → 호스트 콜백)도 동일하게 콜백 기반이다.

### 4.2 정합성 판단

- readiness-tracks-design.md:150은 WASM을 0.8 스코프로 미뤄둔 선례일 뿐 기술
  방향 제약은 아니고, roadmap-design.md:127,138은 "WASM 코어 — 브라우저 직결
  표면, 스파이크 선행(코덱 3벌 문제 재발 방지)"을 명시했다. "코덱 3벌 문제"는
  바인딩 생성기가 언어별 코덱을 다시 찍어내던 과거 문제 — **생성 TS 코덱
  (rkyv-codecs.ts)을 그대로 재사용**하는 한 재발하지 않는다(§7.2).
- wasm-bindgen의 이점(JsValue 직접 전달, wasm-bindgen-test, 번들러 플러그인)은
  **바이너리 와이어가 경계인 이 프로젝트의 계약과 직교**한다. 코덱/해제/에러
  정규화 계약이 전부 FFI 헤더 레벨에 있으므로(ffi_prelude.rs, ffi_free_guard.rs),
  glue가 얇을수록 4호스트 패리티가 유지된다.
- 결론(설계로 이어짐): **A(손수 glue, 스파이크 ABI의 코어 승격)**. 단 스파이크의
  `spike_*`를 그대로 쓰지 않고 표준화된 스테이징 표면으로 일반화해야 한다(NOTES.md
  production 항목 3이 지적한 대로 "a production host ABI would standardize an
  alloc/export pair (or caller-buffer `*_into` entries...)").

### 4.3 선형 메모리 버퍼 재구성/해제 계약과 기존 FFI 해제 경계의 대응

- 기존 경계: Rust 할당 → `(ptr,len)` 반환 → 호스트 복사 → `rustra_ffi_free(ptr,len)`
  정확히 1회(ffi_lifecycle_entries.rs:96-109 계약문). caller-buffer 변형
  (`*_into`, probe→write 2단계 + probe 캐시로 비멱등 핸들러 1회 실행 보장,
  ffi_buffer_entries.rs:42-101)은 Bun이 재사용 버퍼+재시도로 소비한다
  (bun-ffi.ts:104-142).
- wasm 대응: (1) 응답 반환 경로는 동일하되 ptr이 선형 메모리 오프셋이고,
  JS는 `memory.buffer` 뷰를 **grow 후 재취득**해야 한다(스파이크 프로토콜 5단계).
  (2) 요청 투입은 역방향이다 — JS가 wasm 메모리에 써야 하므로 wasm 측
  할당자(`spike_alloc` → 표준화 시 `rustra_wasm_alloc` 등)에서 스테이징 영역을
  빌리고 쓰고, 반납(unstage)한다. 호스트가 wasm 메모리 밖에서 malloc할 수 없는
  제약(wasm3-smoke-main.c 주석 "host cannot malloc in wasm")이 이 ABI를 강제한다.
  (3) free_guard의 (ptr,len) 검증은 오프셋에도 그대로 작동한다 — usize 키이므로.

## 5. 이벤트/채널 전달 — 폴링 drain 선례의 재사용 가능성

### 5.1 wasm엔 푸시가 없다(콜백 import 없이는)

푸시의 실체는 함수 포인터 콜백(§2.3)이므로, import 없이 순수 exports만 쓰는
1차 설계에서는 **폴링 drain이 유일한 경로**다. 선례 2종이 이미 있다:

1. **node loop-stdio의 프레임 펌프**: `packages/node/src/node-loop.ts` —
   `[len u32 LE][frame]` 누적 버퍼 파서(drainBinaryFrames, :348-362), 예약 cmd id
   분기(0xfffd 푸시/0xfffc 채널, :364-367), 리스너 예외 격리(:371-399),
   `__drainEvents` 예약 커맨드(:433-439), `drain(timeoutMs=5s)` + 폴링 간격
   10ms 루프(:720-734). 이 구조는 "호스트가 주기적으로 drain을 당겨 큐를
   소진한다"는 계약의 원형이지만, **전송층(자식 프로세스 stdio)이 wasm에는 없다** —
   재사용 대상은 drain 계약과 프레임 규약이지 stdio 파이프 자체가 아니다.
2. **RN pollMs(731bbae9)**: `packages/react-native/src/react-native-events.ts:87-116` —
   `SubscribeOptions.pollMs`, 네이티브 인스턴스당 폴링 타이머 1개(WeakMap),
   마지막 구독 해제 시 정지, drain 실패는 로그만(:97-108). "CallInvoker 없는
   호스트"용으로 만들어진 이 패턴은 **wasm(콜백 import 없는 호스트)과 정확히
   동형**이다 — `drainEvents()` 하나만 네이티브(=wasm export)가 노출하면 된다.
   이벤트 버스 자체도 이미 드랍-올데스트 정책 + capacity 1024 + 드랍 카운터를
   갖는다(events_bus.rs:16-48) — 폴링 소비와 정합.

### 5.2 채널

채널 전달은 `rustra_ffi_channel_send` → 등록된 콜백(ffi_channel.rs)이라
폴링 drain 표면이 없다. 1차 스코프에서 `channels: false`(EngineSupports)로
선언하는 것이 정직하다 — 콜백 import 기반 설계는 후속 슬라이스 과제.

### 6.2 ③의 전제 조건 확인

wasm3 스파이크 배경에는 "wasm32 **without atomics**" 제약이 명시돼 있다
(compatibility-matrix.md:143-144, NOTES.md). `--target-feature=+atomics`

- `+bulk-memory` 빌드와 SharedArrayBuffer는 브라우저에서 교차 오리진 격리
  (COOP/COEP) 응답 헤더를 요구한다 — 외부 사실이며 본 저장소에서 실측하지
  못했다(**미확인**). 어느 쪽이든 1차 스코프에서 배제 근거로 충분하다(배포 장벽이
  프레임워크 채택 장벽이 된다).

### 6.3 ①의残余 위험

- async fn 커맨드: 첫 poll 완결 시 정상, Pending 시 busy-spin(§2.2 실험). 1차
  설계는 "sync fn 커맨드 + 첫 poll 완결 async fn"만 지원 계약으로 명시하고,
  async FFI 엔트리는 wasm에서 `unsupported` 에러 프레임(§2.1 스파이크 권고)으로
  차단해 spawn 경로를 원천 봉쇄한다. block_on Pending은 코드 검토로 막을 수
  없으므로(런타임 동작) 문서 계약 + doctor 경고로 다룬다.
- 긴 핸들러 블록: 기존 RN JSON 어댑터의 `timeoutPreemption: false` 선례
  (react-native-core.ts:53-59)와 동일하게 정직하게 노출하면 된다.

## 7. 패키지 계약과의 정합 (어댑터가 낄 자리)

### 7.1 엔진 계약 — `RkyvV2SchemaNative`만 구현하면 된다

`packages/types/src/public.ts`:

- `EngineSupports`(:27-34): cancellation/batch/events/channels/timeoutPreemption 5셀.
- `EngineClient`(:36-59) + `RkyvV2Engine`(:113-123) — invoke/invokeById/invokeBatch/
  refreshLiveSchema.
- 핵심: `createRkyvV2Engine(native, registry, options)`(packages/types/src/rkyv-engine.ts:20-35)는
  **네이티브 표면을 `RkyvV2SchemaNative`로 추상화**한다 — 필수는
  `invokeRkyvV2(payload: ArrayBuffer): ArrayBuffer | ArrayBufferView` 단 하나,
  옵션 `getSchema`/`getSchemaGeneration`/`getContractHash`(live-schema.ts:20-41).
  RN/Bun 어댑터가 모두 이 코어 엔진을 공유한다(react-native-core.ts,
  bun-ffi.ts). **wasm 어댑터도 스테이징 glue가 이 인터페이스만 만족시키면
  인젝션/라우팅/배치/계약검증 전부를 무상 재사용**한다.
- `EngineSupports` 선례값: RN rkyv V2(cooperative/single-crossing/push/channels:true/
  timeoutPreemption:true, react-native-core.ts:68-74), RN JSON(shallow/per-entry/none/
  true/false, :53-59), Bun FFI(shallow/per-entry/push/false/true, bun-ffi.ts:41-47).
  wasm 1차 값은 설계 문서에서 확정.

### 7.2 코드젠 조합 — 생성물은 호스트 독립적이다

`examples/calculator/generated/`: commands.ts/contract.ts/rkyv-codecs.ts/
rkyv-registry.ts는 호스트 무관하고, 호스트 엔트리포인트(node.ts/bun.ts/
react-native.ts/tauri.ts)만 부트스트랩 팩토리 차이(bun.ts:1-25,
react-native.ts:1-17). wasm 엔트리포인트(`wasm.ts`)는 `createWasmBootstrap`류
하나를 추가하는 동일 패턴이다. TS 코덱이 이미 ArrayBuffer를 생산
(`RkyvV2Codec.encode(args): ArrayBuffer`, public.ts:131-147, encodeInto 재사용
버퍼 포함)하므로 **코덱 3벌 문제(roadmap-design.md:138)는 발생하지 않는다** —
인코딩은 JS, 디코딩도 JS, wasm은 바이트를 왕복할 뿐.

### 7.3 부트스트랩 수명 — `BootstrapState` 3종 준수

`packages/types/src/bootstrap-lifecycle.ts:15` — `'initializing' | 'ready' |
'disposed'`; dispose 멱등, dispose 후 ready loud-fail(:17-26), reload의 상태
규칙(:8-13). 4호스트 전부 동일 계약(compatibility-matrix.md:106-125). wasm
인스턴스 수명(instantiate → 검증 → 사용 → 참조 해제/재인스턴스)도 이 상태 머신에
그대로 얹을 수 있다 — 스파이크가 "in-app engine swap, no restart"를 기기에서
증명했으므로(compatibility-matrix.md:138) reload 슬라이스의 실현 가능성도 확보됐다.

### 7.4 에러 코드 표면

`RustraErrorCode`(packages/types/src/errors.ts:138-)에 wasm 전용 코드 부재 —
`SyncUnavailable`('sync.unavailable')·`PlatformUnavailable`('platform.unavailable')·
`FfiNotRegistered` 등의 명명 관례를 따라 wasm 미지원 표면(예: async 엔트리)의
코드를 설계에서 정한다. 스파이크 NOTES 권고 문구는 `invoke.unsupported_on_wasm`.

## 8. 문서·정책 정합 체크

- compatibility-matrix.md:57-61(Platforms not covered by runtime evidence) —
  wasm 실행 증거는 시뮬레이터/에뮬레이터(wasm3 경유)로 한정되어 있다고 명시 중.
  JS 브라우저 호스트 착지 시 이 절 + 매트릭스 본문(플랫폼 행) 갱신 대상.
- gap-analysis 리서치(2026-09-03-20-08-17-production-readiness-gap-analysis.md:94):
  "wasm은 dev-only 자체 규정(CI는 컴파일 check만)" — 본 트랙은 이 규정을
  해소하는 방향(런타임 증거 + 발행 패키지)으로 설계해야 한다. release guard
  (§1.4)가 dev-only 유지를 강제하므로, 패키지 발행 형태 결정이 수반되어야 한다.
- versioning-policy: 신규 패키지/표면은 0.x 마이너 레인으로 발행(버전 정책 표).
  실험 표면 관례는 compatibility-contract.md의 per-adapter stable scope 참조.

## 9. 오픈 질문 (설계로 넘기는 것)

1. async fn 커맨드의 첫-poll-완결 요구를 어떻게 계약화할 것인가 — 정적 검사
   가능한가(매크로 레벨), 런타임 계약 문서+doctor로 충분한가.
2. 이벤트 drain export의 반환 포맷 — 기존 NDJSON drain 페이로드셰이프(loop_stdio.rs:59,
   node-loop.ts:671-678 `{name,payload}[]`) 재사용 여부.
3. 스테이징 ABI를 코어 export로 일반화할 때의 이름/게이트 전략 — 항상 노출 vs
   `#[cfg(target_family = "wasm")]`(다른 호스트 심볼 표면 영향).
4. 브라우저 외 Node/Bun/Deno에서의 `@rustra/wasm` 부가가치 — 어느 환경을
   1차 지원 표면으로 문서화할 것인가(세 환경 모두 `WebAssembly` global 보유).
5. 바이너리 크기 최적화 상한 — `wasm-opt`/`wasm-gc` 미적용 실측값 기준 예산
   설정 및 CI 게이트 형태(bench receipt 패턴 재사용 여부).
6. Web Worker 타깃을 1차에 포함할지 — 실행 모델 ①과 ③은 배타적이지 않다
   (동기 export는 Worker 안에서도 그대로 동작). COOP/COEP는 ③의 SAB에만 필요.

## 결론

격자로 요약하면: **컴파일(O)·기기 증거(O, RN/wasm3)·빌드 오케스트레이션(O,
dev 타깃)·JS 어댑터(X)·코어 스테이징 ABI 표준화(X)·이벤트 drain export(X)·발행
형태(X)**. 비호환 요소는 전수 조사 결과 3类(스폰 트랩·park no-op busy-spin·
콜백 import)로 수렴하고, 그 전부가 "sync + 폴링" 스코프에서 회피 가능하다.
바인딩 전략은 손수 glue(raw exports)가 프로젝트 성향·기존 계약·실측 성능
모두에서 우위다. 상세 결정은 `docs/plans/2026-09-07-wasm-host-design.md`.
