# Nitro 재측정 — 구현 후보

동기 공개 API, 생성 코덱의 반복 작업, Rust 직렬화와 숫자 호출의 불필요한 할당을 개선했다. 최종 후보를 iOS Simulator와 물리 Android에서 각각 5회 실행했고, 매회 90개 항목의 정답과 계약을 검증했다. 이 문서는 **작업 중인 0.10.2 기반 소스의 결과**이며 새 버전 발행 기록이 아니다.

**전 항목 Nitro 동급 이상 목표는 아직 충족하지 못했다.** 공개 동기 30항목 중 iOS는 18개, Android는 19개가 동급 이상이다. 느리거나 불확실한 항목을 제외하지 않는다. 원본 10회 결과, 180개 판정, 소스·설치 입력·바이너리 hash 및 중간 실험은 [버전별 결과 JSON](../benchmark-receipts/2026-09-16-nitro-parity-candidate.json)에 보관했다.

## 무엇이 바뀌었나

- `bindSync`는 동기 명령을 한 번 확인하고 호출 함수를 만든다. 호출 시에도 엔진 세대와 동일한 native core·생성 계약을 확인한다. 기존 Promise API는 유지한다.
- 생성 C++ 코덱은 고정 속성 이름을 호출 안에서 한 번 만들고 반복문에서 사용한다. optional 값과 map key 변환의 중복 작업을 줄였으며, 외부 소유 버퍼는 실제 backing store 크기를 Hermes에 신고한다.
- Rust complex 코덱은 짧은 map의 임시 할당과 응답 헤더·본문의 중복 버퍼를 줄였다. 정수 배열은 원래 검증·지연 역직렬화 의미를 유지하면서 반복 분기를 줄였다.
- 숫자 raw FFI는 존재 여부만 필요한 곳에서 입력 형태의 소유 복사본을 만들지 않는다. 동결된 명령은 빌려 쓰며, 변경 가능한 레지스트리는 잠금을 놓고 소유 핸들을 유지한다. raw 경로의 stack 기반 postcard 변환은 남아 있다.
- Android 결과 전송은 모든 측정과 JSON 생성 후 조각 사이에 대기한다. 측정 시간에는 포함하지 않는다.

## 해석과 남은 경계

- 표의 비율은 Rustra 시간 / Nitro 시간이다. 실행별 평균 비율 5개의 로그 Student-t 95% CI이며 작을수록 Rustra가 빠르다. CI 전체가 0.95–1.05 안이면 동급, 상한이 1.0 미만이면 우위다. 판정의 중첩 처리 순서는 원래 validator와 동일하다.
- 각 실행은 3회 준비 후 31개 batch를 측정하고 호출 순서를 번갈아 바꾼다. p50/p95는 batch당 호출 평균의 분포이며 개별 호출의 꼬리 지연은 아니다.
- 양쪽에 동일한 flat arena·DFS·dense index·전체 교체 알고리즘을 사용했다. 재귀 DTO의 Nitro 생성 실험은 실패했으므로 재귀 객체 전달의 동급을 주장하지 않는다. 초기 빈 저장소의 구축 비용은 별도 미측정이다.
- 입력 변환·왕복·저장된 트리 DFS·인덱스 조회는 서로 다른 비용이다. 전체 입력 경로의 개선을 DFS 알고리즘 개선으로 해석하지 않는다.
- iOS는 M1 Max 호스트의 iPhone 17/iOS26.2 Simulator, Android는 Lenovo TB710FU/Android16/arm64-v8a 한 기기다. 서로 다른 플랫폼 결과를 합치지 않는다.
- Nitro/nitrogen 0.37.1, RN0.81.5, Hermes Release를 고정했다. Android 모델·빌드·ABI·APK hash를 실제 기기에서 수집했다. vendor battery 출력의 fake-sensor 표기를 그대로 보관하며 온도 정확도를 보증하지 않는다.
- 이전 버퍼 결과는 Rustra 쪽 외부 메모리 신고가 빠져 있어 공정한 우위 근거로 쓰지 않는다. 최종 후보는 양쪽 모두 신고한다. GC의 구현별 인과 비중은 별도 계측하지 않았다.
- Android 64KiB 공개 동기는 Rustra의 p50이 낮지만 실행별 평균 비율 CI는 1.769–1.827로 느림이다. 긴 표본의 영향을 p50으로 가려 우위라고 주장하지 않는다. 1MiB의 큰 차이도 GC 원인 규명이나 모든 크기의 우위를 뜻하지 않는다.
- 작은 map 개선은 큰 map에서 요청 할당 바이트가 늘어나는 절충이 있다. 상세한 42항목과 반례는 아래 core 보고서에 있다. 요청 바이트는 RSS 또는 최대 사용량이 아니다.

## 남은 원인과 후속 검증

문자열·pair·indexed·resident는 숫자 raw 경로가 아니다. 작은 framed 요청과 응답은 이미 inline/stack 버퍼를 쓰고, 정상 응답은 한 번 직렬화한다. 따라서 이 경로의 차이를 항상 요청 heap 할당이나 두 번의 FFI 때문이라고 설명할 수 없다. Rustra에는 소유 String 구성과 postcard 왕복, 생성 객체의 속성 이름 처리가 남고 Nitro는 C++ DTO 경계를 사용한다. 각 단계의 정확한 시간 비중은 아직 분리 계측하지 않았다.

resident는 양쪽 모두 보관된 트리를 잠금 안에서 같은 DFS로 탐색한다. 매번 전체 입력을 다시 해독하지 않는다. 노드 수에 따라 늘어나는 차이를 작은 indexed 호출의 고정 차이만으로 설명할 수 없으며, f64→index 변환·분기·구조체와 컨테이너 배치·최적화된 루프 차이를 확인해야 한다. 플랫폼별 결과가 다르므로 하나의 원인을 확정하지 않는다.

후속 실험은 세 범위로 한정할 수 있다: 세대 검사를 보존한 공개 JS closure 결합, bind 시 명령별 codec 함수 선택과 현재 switch의 비교, 그리고 동일한 DFS 본문을 유지한 Rust/C++ core-only 원인 분리다. 모두 아직 채택하지 않은 가설이며 더 빠르다는 보장은 없다. 입력·출력 계약을 줄이거나 DFS를 indexed 조회로 바꾸어 수치를 맞추지 않는다.

## 중간 후보와 실패 기록

첫 native 후보는 공용 속성 캐시 조회로 작은 호출이 느려져 호출 내부 소유 방식으로 교체했다. 중간 후보 1과 3의 iOS 5회 결과도 JSON에 남겼다. 후보 2는 빌드만 했고 측정하지 않았다. 후보 3 Android는 계산을 마쳤지만 61개 조각 중 55개만 수집해 실패 처리했다. 부분 결과를 집계하지 않았고 원본 로그와 실패 상태를 보존했다. 전송 보완 뒤 최종 후보를 처음부터 다시 측정했다.

정수 배열의 inline 속성 실험은 다른 DFS 대조군 회귀 때문에 채택하지 않았다. 초기 공개 동기 중간 빌드에는 설치된 native 파일이 오래된 문제가 있었고, 그 수치는 최종 계약 검증의 증거로 쓰지 않는다. 최종 후보의 설치 입력은 소스와 별도 hash 대조했다.

## 검증과 관련 문서

소스 검증 기록은 Rust workspace 534개 통과·5개 ignored, types 271개, CLI 318개 Node + 28개 Bun, 실제 Hermes 경계 457개 assertion, architecture 4개 통과 및 타입·형식·clippy·API snapshot·생성물 검사다. 이후 숫자 raw 변경과 전송 변경은 각각 별도 결정적 회귀 테스트와 변경 범위 검토를 거쳤다. 전송은 25개 테스트·180개 assertion이다. raw 변경은 Debug 7개와 Release allocator 검증을 통과했고, 최종 API snapshot·생성물 검사도 통과했다. 최적화된 Release의 숫자 FFI 한 호출에서 임시 할당 1회·2바이트가 0회로 줄었다. 이 작은 fixture의 결과를 모든 호출의 무할당으로 확대하지 않는다.

이 작업의 추가 무작위 스트레스 검사는 사용자 요청으로 중단했다. 기존 H1/H2 Miri68개, H3 Miri2개와 macOS ASan218개 검증은 각각의 소스 범위에 해당한다. 최종 후보의 성공한 fuzz 또는 Linux LeakSanitizer 검증으로 바꾸어 표현하지 않는다.
