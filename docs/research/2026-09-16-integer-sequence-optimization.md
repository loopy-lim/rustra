# 복합 정수 배열의 반복 분기 개선

[작은 map과 응답 버퍼 개선](2026-09-16-codec-scratch-and-frame.md)을 반영한 H2와, 직접 정수 배열을 읽는 H3 후보를 비교했다. 이 결과는 Rust `Package::invoke_frame`의 재귀 ComplexSerde 경계이며, Nitro 또는 실제 앱의 성능을 대신하지 않는다.

독립 프로세스 5회씩 42항목을 비교한 결과, 큰 정수 배열은 약 23%, 8,191노드 전체 입력 탐색은 약 7%, 같은 트리 왕복은 약 4% 추가로 빨라졌다. [전체 수치·실행파일·소스 hash와 채택하지 않은 실험](../benchmark-receipts/2026-09-16-integer-sequence-optimization.json)을 함께 보존했다.

## 구현

동일한 정수로 구성된 배열은 원소마다 스키마 노드, 배열 종류, 깊이, 부호 여부를 다시 확인하던 비용을 줄였다. 배열 진입 시 조건을 확인하고, 해당 정수 배열에 맞는 역직렬화 경로를 선택한다. tuple, 참조, 다른 타입은 기존 경로를 사용한다. 특정 트리 모양이나 benchmark 명령 이름을 검사하지 않는다.

입력 바이트는 실제 Deserialize 요청 시점에 읽는다. 좁은 정수 범위, u64 전체 범위, 부호, 길이·깊이, 잘린 입력, 남는 바이트, 사용자 정의 Deserialize의 지연 동작을 유지한다. 일반 사용자 코드에서 사용하는 경로에 적용되며 검사나 소유권을 우회하지 않는다.

## 채택과 비용

모든 42항목의 할당 횟수와 요청 bytes는 H2와 동일하다. 정수 배열의 반복 처리 시간을 줄인 변경이며 메모리 감소를 추가로 주장하지 않는다. 작은 optional-none은 약 1.9%(95% CI 1.4–2.3%) 느려졌다. 순수 DFS control은 약 -0.9–+0.9%였고, 일부 매우 짧은 항목은 구간이 넓다.

앞서 세 함수의 인라이닝만 강화한 별도 실험은 채택하지 않았다. 입력 탐색은 개선됐지만, 변경하지 않은 DFS·resident control 다수에서 10–14% 회귀가 반복됐기 때문이다. 원인에 대한 정확한 기여도는 측정하지 않았으며 알고리즘이 바뀌었다고 해석하지 않는다. 이 실험의 실행 결과도 제외하지 않고 별도로 기록했다.

H2 실험과 H3 실험은 각각 따로 실행했다. 두 비율을 곱해 최종판과 최초판을 직접 비교한 결과처럼 제시하지 않는다.

## 측정과 검증

동일 H2 실행파일과 H3 실행파일을 순서를 바꾸며 각각 5회 실행했다. 2개 suite의 42항목을 모두 포함했고 제외한 실행은 없다. Criterion 설정과 paired log-ratio Student t 95% CI는 앞선 문서와 같다. 측정 중 네이티브 빌드나 다른 무거운 검사를 실행하지 않았다.

복합 코덱 검사 68개, H3의 Miri 정수 배열 검사 2개, macOS AddressSanitizer 검사 218개가 통과했다. Linux LeakSanitizer 결과는 이번 후보에서 확보하지 않았다. 추가 스트레스 검사는 중단했고 기존 퍼징 파일은 변경하지 않았다. 초기 테스트가 잘못된 변환 경로를 선택했던 기록은 보존하며 성공한 퍼징 결과로 세지 않는다. 실제 명령 경계의 정수 최소·최대값과 잘못된 입력은 일반 회귀 테스트로 확인한다.
