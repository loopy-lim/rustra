# 공개 호출 CPU 관찰과 속성 이름 재사용 후보

실제 Release 앱의 공개 `bindSync` 경로와 Nitro 0.37.1을 관찰했다. 작은 결과 객체에는 반복되는 고정 속성 이름 생성 비용이 있었다. 큰 트리의 변환과 보관된 트리의 탐색은 별도 비용으로 확인됐다. [앞선 잔여 분석](2026-09-16-nitro-parity-followup.md)의 후속 작업이며, 최종 채택과 공개 성능 판정은 아래 검증 결과로 구분한다.

## 관찰 방법과 원본

생산 네이티브 코드는 `c3bed5dc`의 실행 파일을 그대로 사용했다(SHA256 `5975967fc1dc951c0280a2ade23010b5e8a1e3421ab98520bbb92811992511f1`). 별도 `rustra-nitro-profile/v1` 모드가 원래 fixture의 전체 사전 검증을 수행한 뒤, 한 프레임워크의 고정 입력 호출을 15초간 실행한다. 모든 반환값을 소비하고 체크섬을 검사했다. 10초 CPU 샘플 수집과 종료 처리가 실제 ACTIVE 구간 안에 있었음을 8건 모두 확인했다. 대상은 iPhone 17 / iOS 26.2 Simulator, Hermes Release이며 물리 iOS·Android CPU 관찰 결과는 아니다.

콜드 URL과 URL 이벤트를 사용한 처음 두 시도는 ACTIVE 이전에 실패했다. CPU 샘플이 없으며 실패 기록을 보존했다. 이후 각 JS 번들에 정확한 실행 계획을 넣는 기존 대체 경로로 8건 모두 완료했다. 실행 파일·네이티브 프레임워크는 같고 JS 번들별 해시·계획은 따로 보관했다. 수집기를 개선해 거절된 완료 영수증도 먼저 저장하고, 잘못된 날짜가 시간 구간 검사를 통과하지 못하도록 했다. 최종 검사를 기존 8건에 다시 적용했다.

[영수증·소스/바이너리 식별 정보·빌드 절차](../benchmark-receipts/2026-09-16-nitro-call-profile.json)에 각 실행과 압축 원본 CPU 스택의 경로·해시가 있다. 원본은 `gzip -dc`로 복원할 수 있다. 프로파일 도구의 재현 기준 커밋은 `a5929bd7`, 진단 소스 fingerprint는 `c4963e14ef5cce7e27ceee385513fcbaf4b3c5e7ecc0fdf75980c38a625e04bd`다. 원래 v2의 입력·순서·합격 기준을 바꾸지 않았다.

## 비용을 구분한 결과

pair의 475는 두 호출 지점의 포괄 샘플이며 `createPropNameIDFromAscii` 함수 안에서만 센 수가 아니다. 해당 함수의 최상위 프레임만 별도로 합치면 457이다. 수집된 스택의 정확한 줄 번호와 포함 관계를 [상세 판독 기록](../benchmark-receipts/2026-09-16-nitro-call-profile-findings.md)에 남겼다.

Nitro의 생성 PairPayload 변환기는 설치된 `PropNameIDCache`에서 고정 이름을 재사용한다. 그 조회도 비용이 있으므로 캐시가 공짜라고 가정하지 않는다. Nitro의 큰 트리 왕복 역시 JS ↔ 네이티브 객체 변환이 크며, resident DFS는 8,280개 중 8,093개가 resident 메서드 안에 있었다. 양쪽 모두 resident DFS에서 약 98%가 이 경로라는 사실은 탐색 자체를 별도로 분석해야 한다는 근거이며, Rust/C++ 언어의 본질적 속도 차이를 증명하지 않는다.

## 일반 코덱 개선 후보

각 네이티브 동기 호출 함수가 자기 명령의 유한한 입력·출력 속성 이름을 불변 C++ 문맥으로 소유한다. 호출 중에는 강한 참조를 별도로 유지하므로 재진입·GC·설정 변경 중에도 바깥 호출의 이름이 유지된다. 컨텍스트는 명령 ID를 함께 소유하며, 결과 객체·입력값·동적 맵 키·버퍼를 캐시하지 않는다. 런타임 주소를 키로 쓰는 전역 표나 JS 전역 캐시는 추가하지 않았다.

공통 postcard 인코드/디코드 본문을 공유하고, 기존 Promise/레거시 경로는 호출마다 이름을 소유하는 기존 방식과 순서를 유지한다. 기존 경로에 새 heap vector를 만들지 않도록 고정 배열을 사용한다. 생성 헤더의 새 capability 표시가 없으면 이전 경로로 컴파일된다. raw·직접 버퍼 결과도 실제 스키마의 출력 이름을 사용한다. 복잡한 IR 렌더러는 기존 구현을 그대로 호출하며 이번 이름 재사용의 적용 범위에 포함하지 않는다.

소유권 근거는 설치된 RN 0.81.5 JSI의 관리된 HostFunction 소멸 계약이다. 런타임 연관 객체는 런타임 종료 전 또는 관리된 HostFunction 소멸 중 해제할 수 있고, 런타임 인자를 받지 않는 소멸자는 다른 스레드에서도 가능하다. 이번 문맥은 그 함수와 짧은 동기 호출 내부에만 보관하고, 비동기 작업·전역 코어·다른 런타임에 넘기지 않는다. 같은 코어 검증/호출/해제, getter 순서, 오류, 한 번의 핸들러 실행을 유지했다.

이 설계는 바인딩 생성 시 보관할 이름과 C++ 저장소가 늘어난다. 새 함수 생성을 매번 반복하는 사용의 성능이나 전체 VM 메모리 감소를 주장하지 않는다. 채택 판단은 바인딩을 재사용하는 공개 호출의 전후 측정과 기존 전체 행렬에 따른다.

## 정확성·호환성 검증

- 프로파일/기존 parity 검사 50개, RN 타입 검사 통과. 캡처 8건의 ACTIVE 구간·체크섬을 최종 검증기로 재검증했다.
- 생성기 검사 109개, 생성기 및 테스트 타입 검사 통과. 임의 필드명·중첩/벡터·tuple·raw/buffer·unit·complex passthrough를 검사했다.
- 실제 Hermes 최종 1,375개 단언, 실패 0. 일반 span의 서로 다른 `first`/`second` 출력, 반복 호출의 고정 이름 생성 0회, 동적 키 생성 유지, 재진입·GC·함수 참조 제거·런타임 종료·동시 독립 런타임·decorator 주소 재사용·오류 시 생산 코어 해제를 검사했다.
- 새 어댑터와 이전 identity/no-context 생성 헤더: 실제 Hermes 1,129개 단언 통과. identity 선언/함수까지 없는 헤더: 컴파일·링크와 기존 typed 호출 결과 7을 확인했고, 추가 동기 바인딩은 의도대로 거절됐다.
- C++ codec/wire/core 검사, canonical native identity 컴파일 검사, 공개 bindSync의 재설정·오류·소유권 검사 10개 통과. 두 RN 예제의 정식 codegen 갱신 및 check 통과.

첫 Hermes 시도는 새 테스트가 number[] 폴백의 기존 ArrayBuffer 생성자 조회까지 금지해서 두 런타임에서 실패했다. 해당 폴백에 필요한 조회 1회만 정확히 허용하고 고정 이름·NativeState 조건은 유지했다. 생산 코드를 그 검사에 맞춰 바꾸지 않았다. 첫 codegen check는 생성 파일 자체의 차이가 아니라 관리 manifest가 뒤처져 실패했으며 정식 생성 명령으로 두 예제를 갱신했다. 초기 실패와 최종 실행 기록을 함께 보관한다. 새 무작위·fuzz·스트레스 검사는 추가하지 않았다.

## 전후 측정

최종 수치와 채택 판단은 고정 후보의 측정이 끝난 뒤 이 절에 기록한다. 사전 계획은 iOS의 기존/후보 순서를 AB, BA, AB, BA, AB로 둔 다섯 쌍이며, 각 프로세스는 기존 v2 전체 90개 항목을 실행한다. 후보의 다섯 실행은 원래 Nitro 판정에도 그대로 사용한다. Android는 고정한 후보로 원래 v2 다섯 실행을 수행하며, 보존된 이전 집단과의 차이를 인과적 Android A/B 효과라고 표현하지 않는다. 프로파일러 없이 측정하고 느린 표본을 제외하지 않는다.
