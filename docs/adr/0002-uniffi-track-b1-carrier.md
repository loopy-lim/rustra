# ADR 0002 — Track B1: adopting UniFFI as the Kotlin/Swift language carrier

## Status

Accepted — 2026-09-11. Phase 1 (the type-safe per-command API) landed as
work items B1-1 through B1-5.

## Context

After ADR 0001 mechanized rustra's own contract (Track A), the open question
was language coverage: what carries pure Kotlin (Android) / Swift (iOS) hosts
that want to consume Rust without the TS layer? Three options existed.

1. **B2 — own native bindgen**: write Kotlin/Swift code generators directly
   over the postcard/Frame blob ABI.
2. **B1 — Mozilla UniFFI carrier**: uniffi generates the Kotlin/Swift bindings
   and the value transfer.
3. Per-app hand-written FFI — not a product, just repeated labor.

The 2026-09-11 maturity study and the attach spike (cdylib coexistence nm
check, three-language generation, Swift E2E, measured iOS cross-build) supplied
the evidence, and
[`docs/plans/2026-09-11-uniffi-track-b1-phase1.md`](../plans/2026-09-11-uniffi-track-b1-phase1.md)
fixed the direction. This ADR records the confirmed decisions as landed.

## Decision

### 1. The B1 carrier — B2's own bindgen rejected

Kotlin/Swift bindings are generated by uniffi (uniffi 0.32, library-mode
bindgen). The integrity of this surface is owned not by rustra but by
**uniffi's own per-symbol checksums + contract version** — the Track A
philosophy of ADR 0001, applied by the carrier. rustra's
`contract_hash`/`contract.mismatch` gate therefore stays scoped to the blob
transport surface (JSI/Tauri/Bun/Node). Why B2 was rejected: uniffi's maturity
overwhelmingly outweighs the cost of reinventing codecs, lift/lower, and
checksums ourselves, and adding a command is reflected automatically by the
schema walk.

### 2. The core stays uniffi-free — `invoke_typed` is plain Rust

`crates/rustra` does **not** gain a uniffi dependency or feature. Instead:

- `Package::invoke_typed<I, O>(name, &input)`
  (`crates/rustra/src/invoke_typed.rs`) — name→commandId lookup, postcard
  request, the single dispatch path of `invoke_frame` (renamed from
  `invoke_rkyv_v2` in the 0.9 Frame rename). No second JSON
  execution path is forked, so Rust↔TS binary compatibility is preserved
  without code duplication.
- `decode_frame_response`/`decode_frame_error_parts`
  (`crates/rustra/src/frame_error.rs`) — shared response-frame splitting
  helpers.

The uniffi derives all live in the **generated mirror layer of the app crate**
(`uniffi_generated.rs`, attached via `#[cfg(feature = "uniffi")] include!`).
A default build is identical to before, without uniffi. (The plan proposed a
uniffi feature and an object wrapper in the core; that was revised while
landing — see the plan's addendum.)

### 3. Schema-driven mirror generation with documented divergences

The mirror layer is not hand-written — the probe renders
`uniffi_generated.rs` from the schema (fail-closed renderer, no silent skips,
11 unit tests), the file is committed, and a freshness gate (the
`codegen --check` byte comparison — the build is deliberately skipped in check
mode) guards it. The mechanical divergences of types the mirror cannot express
are documented: sets → `Vec` mirrors collected into real `BTreeSet`s on
conversion, fixed tuples → synthetic records (`SpanInputPair`), maps →
inference-based collect, `getSchema()` → live_schema (generation counter
included), channel/resource handle newtypes → u32 + an explicit path table.

### 4. Open error code space — a single-variant record, enum mapping rejected

The generated error type is the single-variant
`RustraCommandFailure.Failure { code, detail, retryable }` (the same shape as
the TS `RustraCommandError`). rustra's error codes are open — down to custom
strings — so a uniffi enum mapping, which would require closing the code
space, is impossible by design — rejected not on trade-off but on
first principles.

### 5. Static loading only — hot-swap excluded

uniffi hosts bind symbols at load time, so this surface is static/release
builds only. It cannot combine with dylib hot-swap (`hot-core`) — the dev loop
stays on the existing TS/JSI path. Phase 1 exclusions: events/channels
(Phase 2 — callback interfaces + foreign traits), async commands (the Rust
command API is synchronous today), and the XCFramework/AAR publishing
pipelines (later).

### 6. Exact pin

The workspace dependency is `uniffi = "=0.32.1"`. Discipline per the measured
churn (maturity study) where generated bindings and runtime helpers break per
minor.

### 7. Out of the api-surface snapshot scope

The macro-generated `uniffi_*` scaffolding symbols never appear in the
api-surface snapshot's collection inputs (`crates/rustra/src`,
`crates/rustra-macros/src`, `packages/*/src/index.ts`) — the scaffolding
resolves into the example app crate's cdylib. This surface's integrity is
governed by decision 1 (uniffi's checksums), so the snapshot scope is not
extended.

## Consequences

- **Positive**: a type-safe Kotlin/Swift surface without developing a bindgen
  of our own. The single source of dispatch truth remains `invoke_frame`,
  and the core stays uniffi-free so default builds stay light. Adding
  commands/types is reflected automatically from the schema.
- **Negative/cost**: two mirror conversions plus an internal postcard round
  trip per call (the price paid for single-wire simplicity — benchmarking is
  follow-up). The documented mirror-divergence list must be maintained as the
  schema evolves. The uniffi exact pin forces version upgrades to be
  all-at-once (core + mirror + committed bindings regenerated together).
  Mobile runtime E2E (Android emulator/iOS simulator smokes, the
  uniffi-android/uniffi-ios CI jobs) lands separately.
- **Neutral**: coexists with the existing tiers (JSI/Tauri/Bun/Node) — no
  behavior change for existing users. Events/channels, async, and the
  publishing pipelines are subjects of follow-up ADRs/plans.
